# CYInvoice V2.5 員工帳戶與發票作廢設計

本文件記錄 CYInvoice V2.5 已確認的產品設計與工程實作基準。它是設計／需求文件，不是新的永久治理規則；永久規則仍以根目錄 `REPOSITORY_RULES.md`、`REPO_POLICY.md` 與 `apps/CYInvoice/PROJECT_RULES.md` 為準。

最新正式 Release 仍為 **V2.4.2**；目前 V2.5 工程基準為 **V2.5.0 Build 3**。VERSION／BUILD、PR merge 或工程測試包都不代表正式 Release 授權。

## 1. V2.5 範圍

V2.5 納入：

- 本機員工清單與帳戶管理。
- 員工密碼驗證與三級權限。
- 唯一超級管理員與離線災難恢復碼。
- 舊 CYInvoice 管理密碼遷移。
- 正式發票作廢核心。
- 作廢原因與操作員工編號送入 AMEGO `CancelReason`。
- 作廢前發票號碼人工 double check、員工身分驗證與責任提示。
- 紙本電子發票證明聯狀態覆核，以及「尚未收回」的主管人工確認流程。
- 作廢送出後以 AMEGO 官方資料確認最終結果。
- 作廢狀態與既有同步、清單、詳細資訊、issue center 與必要 Cache 行為整合。

V2.5 不納入：

- Cloudflare Workers / D1。
- 雲端 API 位址與裝置授權。
- A/B 機員工帳戶同步。
- Email 驗證碼／Email 忘記密碼。
- MO 密碼雲端同步。
- 多台電腦共用登入失敗計數。
- AMEGO App Key 雲端化或現行儲存機制重構。

V2.5 即使完全沒有雲端帳戶服務，也必須能正常使用員工帳戶與員工作廢功能；實際呼叫 AMEGO 開立、查詢或作廢仍需要能連線到 AMEGO。

## 2. 單一本機員工資料模型

V2.5 不建立「單機帳戶系統」與「雲端帳戶系統」兩套邏輯。

```text
V2.5
本機 employees -> CYInvoice

後續版本
Cloud -> 同步 -> 本機 employees -> CYInvoice
```

未來若加入雲端，同一份本機員工資料改作同步後的離線 Cache；CYInvoice 仍讀同一套本機介面，不因有無雲端重寫驗證與權限流程。

每位員工至少包含：

- 員工編號：固定 4 碼數字，唯一。
- 姓名：必填。
- Email：**必填**；V2.5 先保存，後續可供 Email 密碼復原使用。
- 密碼安全雜湊：不得保存明文或可逆密碼。
- 權限角色：`SUPER_ADMIN` / `ADMIN` / `EMPLOYEE`。
- 啟用狀態。
- 建立／最後修改時間。

Email 必填由 UI 與 `EmployeeStore` 底層共同強制，不能只依賴表單驗證。

員工資料存於既有 `Data/CYInvoice.db`，使用獨立 `employee_schema_version` 管理，不改寫既有發票 `schema_version=1` 的語意。

## 3. 三級權限

### 3.1 SUPER_ADMIN

每套本機員工資料只允許一位超級管理員。

超級管理員：

- 具有帳戶管理最高權限。
- 不可降級為 `ADMIN` 或 `EMPLOYEE`。
- 不可取消超級管理員權限。
- 不可停用。
- 不可刪除。
- 一般管理員不得直接重設其密碼。

上述限制必須由業務／資料層強制，不得只靠 UI 隱藏或 disabled 按鈕。

### 3.2 ADMIN

管理員可以：

- 進入帳戶管理。
- 新增員工。
- 修改一般員工／其他管理員基本資料。
- 重設一般員工／其他管理員密碼。
- 啟用／停用一般員工。
- 將一般員工提升為管理員。
- 取消其他一般管理員的管理員權限。
- 處理「尚未收回紙本電子發票證明聯」所產生的作廢人工確認。

管理員不得自行取消自己的管理員權限；一般管理員不得對唯一超級管理員執行降級、停用、刪除或直接密碼重設。

### 3.3 EMPLOYEE

一般員工可以正常使用 CYInvoice，並以自己的員工編號／密碼進行作廢身分驗證；不能進入帳戶管理，也不能批准或取消主管人工確認。

## 4. 超級管理員離線災難恢復

V2.5 使用獨立「超級管理員復原碼」，格式：

```text
CYR-XXXX-XXXX-XXXX-XXXX-XXXX
```

規則：

- 建立第一位超級管理員後自動產生。
- 完整原始碼只顯示一次。
- 本機只保存安全 Hash，不保存可讀回原始碼。
- 超級管理員忘記密碼時，可用「員工編號 + 復原碼 + 新密碼」重設。
- 成功使用後舊復原碼立即失效，並產生新碼只顯示一次。
- 已登入超級管理員可輸入目前密碼主動重新產生復原碼。
- 密碼與復原碼同時遺失時，V2.5 不提供一般管理員後門。
- 不使用 AMEGO App Key 作為復原憑證。

未來 Email 密碼重設可成為額外途徑，但離線復原碼仍保留。

## 5. 舊管理密碼遷移

舊版資料第一次進入 V2.5：

1. 驗證既有 CYInvoice 管理密碼。
2. 建立第一位員工：4 碼員工編號、姓名、**Email（必填）**、新員工密碼。
3. 第一位員工自動成為唯一 `SUPER_ADMIN`。
4. 產生並顯示一次超級管理員復原碼。
5. 清除舊管理密碼 salt/hash，日常管理改用員工帳戶與角色權限。

若第一位超管已成功建立，但清除舊管理密碼時中斷，後續啟動仍應再次完成清除。

全新安裝沒有舊管理密碼時，直接建立第一位超級管理員並產生復原碼。

## 6. 帳戶管理 UI

主畫面有獨立「帳戶管理」入口，與一般「設定」分開。

進入帳戶管理時只要求：

```text
員工編號
密碼
```

只有啟用中的 `ADMIN` / `SUPER_ADMIN` 可進入。

帳戶管理主視窗：

- 標題為「帳戶管理」。
- 不另外顯示「目前管理員」資訊。
- 清單欄位：員工編號、姓名、Email、權限、狀態。
- Email 欄填滿剩餘寬度，不保留看似額外欄位的空白。
- 操作包含新增、修改、變更／重設密碼、啟用／停用、設為／取消管理員，以及超級管理員復原碼重新產生。

V2.5 新增的帳戶、密碼、復原與作廢視窗統一遵循：

- 精簡固定尺寸，不保留大面積無用途空白。
- Label 與輸入欄位在相同視覺基準線。
- 實際輸入欄位一律靠左。
- 復原碼唯讀顯示可置中，因其不是輸入欄位。
- 使用 CYInvoice 應用程式 Icon，不使用 Windows 預設 Form Icon。

## 7. 作廢入口與前置查詢

作廢按鈕只存在發票詳細資料，不直接放在發票清單。

流程：

1. 使用者從清單雙擊發票。
2. 每張發票都先執行 `invoice_query`，不得因本機 Cache 看似最新而跳過。
3. 只有 fresh query 後仍為已開立、沒有 `wait.C0501`、官方 upload status 99，且公司／環境一致的發票才可進入作廢流程。
4. 已作廢、`已開立（等待作廢）`、資料不符、query 失敗、環境／公司不符或其他狀態不確定時，不得再次送出作廢。

V2.5 不另加本機跨期限制；能否作廢以 AMEGO 正式結果為準。

## 8. 作廢原因與 CancelReason

作廢第一步由使用者輸入原因，最多 **10 字**。

AMEGO 官方 `CancelReason` 上限確認為 20 字。CYInvoice 固定送出：

```text
<4碼員工編號> <使用者輸入原因>
```

例如：

```text
3015 退貨
```

4 碼員工編號 + 1 個空格 + 最多 10 字原因，最多 15 字，低於 AMEGO 20 字上限。

UI 與底層共同使用 `EmployeeVoidWorkflowService.MaxReasonLength`，避免畫面與業務規則再次分岔。

若作廢先進入主管人工確認，最後批准送出時仍保留**原申請員工編號**，不改成批准主管編號。

## 9. 發票作廢確認

原因確認後進入「發票作廢確認」。一般發票欄位：

```text
發票號碼  [                    ]
員工編號  [        ]
員工密碼  [                    ]
```

紙本發票另外增加：

```text
證明聯狀態  [未列印／未交付 | 已收回 | 尚未收回]
```

載具等非紙本發票不顯示證明聯狀態。

### 9.1 發票號碼 double check 與背景遮蔽

此欄位的目的，是要求操作員拿 ERP 紀錄、紙本發票或其他正式來源重新核對，而不是直接從 CYInvoice 畫面照抄。

確認視窗：

- 發票號碼輸入欄不得預填。
- 不顯示正確發票號碼。
- 程式只在背景比對輸入值與目前準備作廢的發票號碼。
- 不符時只提示「發票號碼不符，請重新確認」，不得回顯正確答案。
- 不禁止剪貼簿貼上；安全控制重點是移除畫面上的正確答案，而不是限制輸入方式。

進入最終確認後，原詳細頁仍保留背景脈絡，但暫時遮蔽可直接照抄的資訊：

- 左側詳細資料中的發票號碼。
- 詳細視窗標題中的發票號碼。
- 紙本 PDF 預覽或載具模擬發票預覽。

金額、來源、買受人等其他背景資料仍可見。若發票號碼或帳密驗證失敗需要重試，遮罩持續存在；取消或離開整個作廢確認流程後，由同一生命週期一次還原。

遮罩採明確 `Apply -> confirmation session -> Dispose/restore`，不使用 Timer、全域 Dictionary 或視窗 Activated 等事件猜測還原時機。

### 9.2 員工驗證

送出作廢或建立人工確認前必須確認：

- 員工編號合法且存在。
- 員工目前為啟用狀態。
- 密碼驗證成功。

任何驗證失敗都不得呼叫 AMEGO 作廢 API。

帳號不存在、編號格式不合法、停用或密碼錯誤，對外統一為「員工編號或密碼錯誤」。

## 10. 責任聲明

正式責任提示：

> 本人已核對本次作廢之發票號碼、交易事實、作廢原因及紙本電子發票證明聯收回狀況。
>
> 本人了解發票作廢應依相關法令及公司作業規範辦理；如因本人故意、操作錯誤或疏失致生相關問題，願依實際責任歸屬、相關法令及公司規定負應負之責任。
>
> 按下「確認作廢」即表示本人已閱讀並確認上述事項。

確認視窗內上述責任文字**全部使用粗體**。不另設「同意責任聲明」Checkbox；按下紅色「確認作廢」即代表已閱讀並確認。

「作廢」與「確認作廢」使用與其他 StandardButton 相同尺寸與形狀，只以紅底白字 danger 色區分，不另創特殊按鈕造型。

## 11. 紙本證明聯與人工確認

紙本發票必須選擇：

1. `未列印／未交付`：正常作廢流程。
2. `已收回`：正常作廢流程。
3. `尚未收回`：**不立即呼叫 AMEGO，也不呈現為作廢失敗**，改進入「人工確認」。

若選「尚未收回」，確認視窗提示：

> 未收回作廢需由管理員確認後才會送出

人工確認流程：

```text
一般員工提出作廢
→ 發票號碼 + 員工帳密驗證成功
→ 證明聯狀態 = 尚未收回
→ AMEGO 呼叫數 = 0
→ 發票仍維持已開立
→ 上傳問題新增「人工確認」
```

暫存必要資訊：原申請員工編號、作廢原因、提出時間，以及既有發票／訂單識別；不得保存員工密碼。完成後移除暫存資料，不建立永久作廢 audit。

只有啟用中的 `ADMIN` / `SUPER_ADMIN` 可以：

- `確認送出作廢`
- `取消退回`

主管操作時 UI 先驗證帳密，底層服務再次驗證同一管理員帳密與角色。

批准時重新走既有 AMEGO fresh query／pending／防重核心，`CancelReason` 保留原申請員工編號。取消退回不呼叫 AMEGO；若已送出或已有核心 pending marker，禁止取消退回。

人工確認依公司統編與 test/prod 環境隔離。

## 12. 密碼錯誤節流

作廢驗證採本機記憶體內漸進式節流：

- 第 1～2 次：正常重試。
- 第 3 次：約 5 秒。
- 第 4 次：約 15 秒。
- 第 5 次以上：約 60 秒。
- 驗證成功後清除相應失敗狀態。

不做長時間永久鎖帳；不得把密碼、Hash、復原碼寫入 log。

## 13. AMEGO 作廢結果安全語意

正式作廢 API 為 `/json/f0501`。不能僅因 `f0501` 回傳 `code=0` 就把本機狀態當成最終成功。

送出前：

- fresh `invoice_query` / `invoice_status` 檢查。
- 已作廢不重送。
- 已有 `C0501` 待處理不重送。
- 官方狀態不是 99 不送。
- 真正呼叫 `f0501` 前先持久化本機 pending marker，避免 crash／restart 後盲目重送。

送出後：

- 官方明確確認作廢成功 → `已作廢`。
- 官方明確失敗 → 作廢未完成／依狀態重新處理。
- timeout、傳輸結果不明或 `invoice_query.wait` 有 `C0501` → `已開立（等待作廢）`，保留 pending marker，禁止盲目重送。

`invoice_status=99` 表示原發票上傳完成；即使正在等待作廢，99 仍固定顯示「完成」與綠燈，不因作廢流程建立顏色例外。

pending 再次操作時只做 reconciliation；若官方明確仍為正常已開立且沒有待處理作廢，只解除 pending 並要求重新確認，同一次操作不自動重送。

## 14. 同步與 AMEGO 權威

AMEGO 官方資料是發票狀態權威來源。

已確認 API 資料語意：

- `invoice_list` 提供 `cancel_date` 與 `invoice_status`，不提供 `wait[]`。
- `invoice_query` 提供 `cancel_date`，並可由 `wait[]` 的 `C0501` 辨識等待作廢。
- CYInvoice 自己送出作廢後，本機 pending marker 立即維持 `已開立（等待作廢）` 並防止重送。
- 啟動／5 分鐘／手動整理共用既有近 3 天 `invoice_list` 流程。
- list 一旦取得 `cancel_date > 0`，收斂為 `已作廢`、清 pending、使舊 PDF／preview Cache 失效。
- 只有 pending 發票超出近 3 天 list 覆蓋範圍時，才採核准例外：針對該張單筆 `invoice_query` 補充確認；仍不自動重送 `f0501`。
- 每日完整同步維持既有完整同步設計。
- 每張發票雙擊詳細資料都執行 fresh `invoice_query`。
- list、同步 query、詳細 query 共用同一套官方狀態映射，不在不同入口重新解讀同一狀態。

顯示規則：

- 清單：`已開立`／`已開立（等待作廢）`／`已作廢`，一般文字，不為等待作廢加黃底。
- 詳細資料等待作廢：顯示 `已開立（等待 發票作廢）`，只有 `（等待 發票作廢）` 使用黃底強調。
- upload status `99` 永遠為完成／綠燈。

第五批仍需用測試環境實際送出例如 `3015 退貨`，保存完整 `invoice_query` JSON，確認 AMEGO 是否回傳未文件化的作廢原因欄位：

- 若官方 query 可取回原因，正常同步／顯示。
- 若官方 query 不提供原因，不為此另建永久本機 `void_audit`。

## 15. App Key 與 MO 密碼

### 15.1 AMEGO App Key

V2.5 完全維持現行設計：

- 各電腦由管理者自行設定。
- 使用目前 Windows DPAPI 保護。
- 不上雲。
- 不同步。
- 空白設定不得覆寫既有有效 App Key。
- 不作為員工密碼或超級管理員復原憑證。

### 15.2 MO 密碼

V2.5 維持目前本機儲存／使用方式；若因 Windows DPAPI 使用者範圍無法解密，首次帳戶設定要求管理員重新輸入。雲端同步留待後續版本。
