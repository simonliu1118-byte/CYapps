# CYInvoice 功能基準

本文件描述目前 C#／WinForms 工程線產品行為；永久治理規則仍以 `PROJECT_RULES.md` 為準。

- 目前工程測試基準：**V2.6.2 Build 0**。
- 最新公開正式 Release：**V2.4.2**（tag：`cyinvoice-v2.4.2`）。
- V2.6.2 已通過 Windows engineering CI，但仍需實機／光貿驗證；未經使用者當次明確要求不得建立正式 Release。

## 1. 平台與基本開立

- Windows 10/11 x64 可攜式 GUI EXE，C#／.NET 10／WinForms，自 V2.0.0 起為唯一正式產品線。
- 支援手動開立、MO店+、酷澎及鼎新 ERP 匯入開立。
- 手動自動訂單編號格式為 `MYYYYMMDDXXX`。
- 一般消費者只能使用含稅模式；公司統編可切換含稅／未稅。
- 金額使用固定精度邏輯，驗收基準包含 `200 → 190.4761905 → 200`。
- 商品明細最多 50 筆；空白列可忽略，部分填寫列必須補齊後才可送出。
- 品名／數量／單價 Enter 流程為：品名 → 數量 → 單價；單價 Enter 後若已有下一列就移至下一列品名，否則新增一列。
- 發票總備註最多 200 字。

## 2. 防重複與開票安全

- 防重複鍵為「來源＋原始平台訂單編號＋環境」。
- 同來源同原始訂單已有已開立、結果不明、資料變更中或其他未明確可重開狀態時禁止再次開立。
- 明確失敗或已作廢才允許重開；重開 API OrderId 使用 `-R2`、`-R3` 等可追蹤尾碼，本機仍保存原始訂單編號。
- 同一時間只允許一個 CYInvoice 程序；同一程序開立流程序列化「防重檢查 → 建立待處理紀錄 → 送出」。
- AMEGO 已成功開立與本機保存成功是不同狀態；遠端成功但本機保存失敗時不得當一般失敗重送。
- 網路逾時／傳輸結果不明時只做唯讀回查；無法嚴格確認則標記「結果不明」並禁止盲目重送。
- 開票後回查不得只比 OrderId；必須唯一命中並核對必要欄位。
- 上傳狀態只有 AMEGO 明確回覆 `99` 才視為完成；`91` 為錯誤；其餘不得冒充成功。

## 3. 公司統編與買方名稱

- 手動開票與鼎新匯入共用公司統編／買方名稱查詢流程。
- 完整 8 碼統編輸入後自動查詢；API 技術失敗不得冒充「查無名稱」。
- 光貿查得到的公司名稱不存成人工名稱；只有 API 正常但名稱空白、使用者人工輸入且最終確認成功時才保存本機名稱記憶。
- 人工名稱與 API 名稱不同時提示並提供 `↻` 強制重查。
- 過時的非同步查詢結果不得覆蓋使用者後來輸入的新值。

## 4. 測試環境

- 光貿測試環境是共用池；送往測試 API 的可識別資料依測試隱私規則去識別化。
- 公司戶測試開票使用公開測試統編 `28080623`，送出前向光貿查詢其正式名稱。
- 測試環境 API OrderID 使用 CYInvoice technical namespace，避免不同公司／執行個體互相撞號。
- UI 與本機資料仍顯示原始可讀 OrderID，不暴露 technical prefix。
- 測試環境同步不以 `invoice_list` 任意掃描共享測試池，只處理本機已知測試紀錄。

## 5. Excel 匯入

### 5.1 共用流程

- MO店+、酷澎、鼎新 ERP 各自只負責解析來源檔案；解析後都進入共用「開立發票匯入確認」流程。
- 取消、未勾選、資料有問題或結果不明的訂單不得送出。

### 5.2 MO店+

- `OrderExport` 依完整欄名辨識，不依檔名或固定欄位位置。
- 受密碼保護的 `.xls` 由 Excel COM 唯讀開啟，停用巨集、外部連結更新、事件及提示。
- 官方「開立發票金額_依品項」及官方加總欄位是消費者發票金額最高準則。
- 有買方統編者為公司紙本；無統編者走會員載具流程。
- MO店+ Excel 密碼不是首次設定必要欄位；未設定時點擊 MO店+ 必須先提示至設定頁完成密碼設定，且不得先開檔案選擇器。

### 5.3 酷澎

- 支援已寄出 DeliveryList `.xlsx`，依欄名與必要欄位辨識。
- 「應開立予買家之發票金額」是買家發票依據；「應開立予酷澎之發票金額」不得計入。
- 未出貨、公司統編、多商品／多數量、特殊折扣等尚缺可靠樣本的格式採安全停止，不猜測。

### 5.4 鼎新 ERP

- 一個 `.xlsx` 活頁簿只代表一張銷貨單，必須找到「單頭資料」與「單身資料」。
- 單頭必要欄位：銷貨單號、客戶全名、統一編號、本幣合計。
- 單身必要欄位：品名、數量、金額；單位為選填。
- 單身金額是權威值；單價由金額 ÷ 數量推導。
- 單身金額合計必須等於單頭本幣合計。
- 公司戶可在確認視窗修改統編／名稱，修改後必須先按「套用資料」。
- 鼎新一律紙本。

## 6. 本機資料與同步

- 主要資料庫：`Data/CYInvoice.db`；安全設定：`Data/settings.json`。
- 舊 `invoices.json`／`buyer_names.json` 只作首次 SQLite 遷移來源與保留備份。
- AMEGO／光貿官方資料是發票內容權威來源；SQLite 是本機 Cache 加 CYInvoice metadata。
- 程式啟動、每 5 分鐘及手動「重新整理狀態」共用最近 3 天同步核心；同步重疊時直接略過。
- 手動重新整理有 30 秒冷卻。
- 每個本機日第一次正式環境自動同步，校對目前兩月發票期別＋上一期；同日後續回到最近 3 天。
- 雙擊任何發票開啟詳細資訊前一律 `invoice_query` 該張；查詢失敗不得用舊 Cache 冒充最新資料。
- 正式環境本機發票 Cache 只保留目前及上一期；測試環境只保留當日。
- 無法判定日期的紀錄不得靠猜測刪除。

## 7. 員工帳號與權限

- 員工編號固定 4 碼數字。
- 角色：`SUPER_ADMIN`、`ADMIN`、`EMPLOYEE`；UI 顯示為超級管理員、管理員、一般使用者。
- 新密碼至少 8 碼，僅接受 ASCII 英文字母與數字；既有舊密碼仍可驗證，不因規則更新而直接鎖死。
- 全新資料第一次啟動只建立第一位超級管理員；超級管理員唯一，不能降級、停用或刪除。
- 超級管理員建立時產生一次性離線復原碼；SQLite 只保存 Hash，不保存明文。
- 管理員可以管理其他管理員／一般使用者，但不得操作超級管理員，也不得自行取消自己的管理員權限或停用／刪除自己。
- 設定與帳號管理共用同一個「權限驗證」登入視窗，不建立兩套管理員認證機制。

## 8. 發票作廢

- 發票詳細資訊中的「作廢」由一般使用者發起並驗證員工帳密。
- 作廢原因最多 10 個 Unicode rune；AMEGO `CancelReason` 最多 20 字。
- 不需管理員覆核：`使用者編號-原因`，例如 `3015-消退`。
- 需管理員覆核：`管理員編號-使用者編號-原因`，例如 `3001-3015-消退`。
- 紙本發票需確認證明聯狀態；證明聯尚未收回時不直接送出 `/json/f0501`，而建立人工確認待辦。
- 人工確認由管理員在「上傳問題」詳細待辦中執行「確認送出作廢」或「取消退回」。
- 作廢送出後若光貿未確認最終結果，標示 pending，不盲目重送；後續正常同步持續查詢。
- 超過目前＋上一個兩月期別的作廢 pending，可由管理員手動結案；結案不呼叫光貿 API，也不得把本機狀態偽造成官方已作廢。

## 9. 折讓暫行人工流程

### 9.1 折讓申請

- 目前不直接呼叫 `/json/g0401`。
- 一般使用者在發票詳細資訊提出：折讓原因、含稅折讓總額、員工編號、密碼。
- 建立申請前先以 `invoice_query` 取得最新發票及既有 `allowance[]` 基線。
- 申請進入「上傳問題」的折讓人工處理待辦，由管理員到光貿網站人工建立折讓。
- 管理員標記人工操作完成後，CYInvoice 繼續共用 `invoice_query.allowance[]` 查詢新折讓，不另外新增折讓查詢流程。
- 若只有一筆符合的新折讓且金額吻合，系統可確認完成；多筆候選、金額不符或仍處理中時保留待辦，不猜測。
- 已進入官方確認階段的申請不可取消退回。
- 超過目前＋上一個兩月期別仍 pending 的折讓，可由管理員手動結案；結案只清除本機追蹤，不代表官方折讓完成。

### 9.2 已完成折讓歷史

- 發票詳細資訊左側「作廢 / 折讓紀錄」只顯示已完成／官方可確認的歷史；待辦仍留在「上傳問題」。
- 折讓資料來源為 `invoice_query.allowance[]`。
- 雙擊折讓紀錄可開啟折讓詳細資訊。

### 9.3 折讓 PDF

- V2.6.2 起可透過 `/json/allowance_file` 取得官方折讓 PDF。
- 支援官方 `download_style` 0、1、3：A4、A4 (地址+A5)、A5。
- 版型選擇沿用既有 PDF 卡片 UI；不預選版型。
- PDF 下載後通過大小與 `%PDF` 驗證才寫入 `Cache/AllowancePDF`；短效 `file_url` 不保存。
- PDF 使用既有 WebView2／Edge PDF Viewer 顯示。

### 9.4 折讓作廢（V2.6.2 暫行人工流程）

- 目前不直接呼叫 `/json/g0501`。
- 只有 `invoice_query` 中狀態已完成的折讓單可提出作廢申請。
- 一般使用者輸入作廢原因並驗證員工帳密後建立「折讓作廢人工處理」待辦。
- 管理員在光貿網站人工完成作廢後，可於待辦詳細視窗標記已完成；也可在尚未處理前取消退回。
- 目前本版只把人工作業狀態保存在本機，不把「管理員-使用者-原因」寫回光貿；正式 `/json/g0501` 自動化留待後續版本。

## 10. PDF、預覽與列印

- 同環境、已開立、未作廢且有發票號碼的紙本發票可透過 `/json/invoice_file` 取得官方 PDF。
- 紙本詳細資訊使用官方 A4 style 0 第一頁作預覽；完整 PDF 不因預覽而被改寫。
- 發票 PDF Cache 依環境、日期、發票號碼與版型隔離；預覽另存 `Cache/InvoicePreview`。
- 公司統編發票支援 0、1、2、3、5 五種版型；一般消費者固定 A4。
- 「檢視 PDF」使用 WebView2／Edge 原生工具列。
- 「列印發票」直接送往 CYInvoice 記住的雙面印表機，不修改 Windows 全域預設印表機。
- 會員載具不呼叫紙本 PDF API，不建立紙本 PDF／預覽 Cache。

## 11. 上傳問題

V2.6.2 起「上傳問題」使用單一清單，集中顯示：

- invoice list／query／同步／本機寫入／解析／ambiguous match 等技術問題。
- 發票開立失敗紀錄。
- 紙本作廢人工確認。
- 折讓人工處理。
- 折讓作廢人工處理。
- 作廢／折讓等待官方確認及可管理員結案的工作。

行為：

- 人工待辦與一般 issue 由雙擊開啟詳細視窗；操作按鈕不堆在主清單工具列。
- 只有「開立失敗」列可勾選並清除；清除失敗紀錄不得刪除光貿資料。
- Pending／人工工作不得被一般「標記已解決」繞過既有流程。

## 12. 安全設定與 UI

- 正式 App Key 與 MO店+ 密碼使用 Windows 使用者 DPAPI。
- 員工密碼與復原碼使用不可逆 Hash，不保存明文。
- 全新 Data 第一次啟動不可略過超級管理員建立；首次環境固定為測試。
- 設定視窗與子視窗不得因 UI 重構改變發票成功判定、防重或同步語意。
- App 自有子視窗不顯示多餘 title-bar icon；主程式仍保留應用程式 icon。
- 使用者可見的帳號管理名稱統一為「帳號管理」；一般角色顯示「一般使用者」。
