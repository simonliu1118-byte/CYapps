## 1. V2.5 員工帳戶與作廢流程

V2.5 已完成實作前設計，詳細內容見 `V2_5_EMPLOYEE_VOID.md`。本版目標是先完成**完全不依賴雲端即可運作**的本機員工帳戶與正式發票作廢；雲端同步、Email 密碼重設與 Device Token 等功能延後。

### 第一批：員工核心

- [x] SQLite 員工 additive schema／migration；使用獨立 `employee_schema_version`，不改寫既有發票 `schema_version=1`。
- [x] 4 碼唯一員工編號、姓名、Email、Password Hash、啟用狀態、建立／最後修改時間。
- [x] `SUPER_ADMIN` / `ADMIN` / `EMPLOYEE` 三級權限。
- [x] 每套本機員工資料只允許一位超級管理員。
- [x] 應用程式邏輯＋SQLite trigger 雙層強制超級管理員不可降級、停用或刪除。
- [x] 管理員可互相取消對方管理權限，但不得自行降級／停用／刪除自己。
- [x] 超級管理員高強度復原碼：只存 Hash、一次性使用、成功使用後輪替、可由超管主動重新產生。
- [x] 不使用 AMEGO App Key 作為超管復原憑證；App Key 現行 DPAPI 行為完全未改。
- [x] Windows CI 驗證既有 V2.4.2 發票資料加入員工 schema 後仍保持不變，並涵蓋員工身分限制、角色保護與復原碼輪替。

### 第二批：帳戶管理

- [x] 主畫面加入獨立「忘記密碼」「帳戶管理」「設定」入口。
- [x] 「帳戶管理」與「設定」只有啟用中的管理員／超級管理員驗證後可進入。
- [x] 新增、修改、停用／啟用、一般員工／管理員密碼重設與角色調整；日常管理不提供刪除 UI。
- [x] 管理員不得自行降級／停用；一般管理員不得直接重設超級管理員密碼。
- [x] 超級管理員忘記密碼時使用離線復原碼重設，成功後立即輪替新碼；密碼與復原碼同時遺失時不提供一般管理員後門。
- [x] 超級管理員可在驗證目前密碼後主動重新產生復原碼；新碼只完整顯示一次。
- [x] 舊 CYInvoice 管理密碼僅用於 V2.5 首次遷移；建立第一位超級管理員後清除舊 salt/hash 並退出日常管理機制，若首次清除中斷則後續啟動會再次完成清除。
- [x] 全新安裝直接建立第一位超級管理員並產生復原碼；MO店+ 密碼缺少或因 Windows DPAPI 範圍無法解密時要求管理員重新輸入。
- [x] AMEGO App Key 現行本機 DPAPI 儲存及空白保留行為未改，也不作為復原憑證。

### 第三批：AMEGO 作廢核心

- [x] 已重新核對光貿 `/json/f0501`、`invoice_query`、`invoice_status` 官方規格；`CancelReason` 官方上限確認為 20 字。
- [x] 已串接 `/json/f0501`；payload 固定使用一筆陣列並在 client 端限制發票號碼與 `CancelReason` 長度。
- [x] 作廢核心接受最終送出的 `CancelReason`，限制 20 字；第四批組成「4 碼員工編號 + 空格 + 最多 15 字原因」。
- [x] `invoice_query` 已解析 `cancel_date` 與 `wait` 中的 `C0501`；作廢後以 query／status 官方結果確認，不以 `f0501 code=0` 單獨判定成功。
- [x] 結果不明、timeout、官方仍處理中或 code=0 尚未確認時，寫入既有 `extra_json` 技術性 pending marker 並禁止盲目重送；不建立永久 `void_audit`。
- [x] pending 紀錄再次操作時只做 reconciliation；若官方明確仍為正常完成且沒有待處理作廢，只解除 pending 並回傳 retry-ready，同一次操作不自動重送。
- [x] 同一程式內另以執行鎖阻止同張作廢流程並行重複送出；Windows 專用 void tests 已涵蓋並行、防重、timeout、已作廢、待處理、明確拒絕與官方確認語意。
- [x] 作廢後重開既有 `-R2`、`-R3` API OrderID 與防重安全語意未修改，既有 core parity tests 維持成功。
- [x] 不自行新增本機跨期禁止規則；API 是否允許作廢以 AMEGO 正式結果為準。

### 第四批：員工作廢整合

- [x] 詳細資料沿用既有「每次開啟都先 `invoice_query`」流程，只有 fresh query 後仍為已開立且 upload status 99 的發票顯示可用「作廢」入口。
- [x] 作廢原因獨立輸入，最多 15 字；送 AMEGO 時組成 `4 碼員工編號 + 空格 + 原因`。
- [x] 「發票作廢確認」保持精簡：發票號碼、員工編號、員工密碼；紙本發票另外顯示「證明聯狀態」。
- [x] 發票號碼不得預填；確認視窗不得顯示可照抄的正確發票號碼或完整發票資訊。
- [x] 發票號碼必須與目前準備作廢的發票完全一致；錯誤只提示「發票號碼不符，請重新確認」，不回顯正確答案。
- [x] 員工不存在、停用、編號格式不合法或密碼錯誤時，不呼叫 AMEGO；帳號／密碼錯誤對外統一為「員工編號或密碼錯誤」。
- [x] 本機作廢驗證採漸進式短暫節流：前 2 次正常、第 3 次約 5 秒、第 4 次約 15 秒、第 5 次以上約 60 秒；成功後清除相應失敗狀態。
- [x] 責任聲明採「按下確認作廢即表示已閱讀並確認」，不另設同意 Checkbox。
- [x] 紙本證明聯狀態為「未列印／未交付」或「已收回」時可依正常作廢流程送出；「尚未收回」時不呼叫 AMEGO、不判作廢失敗，改建立「人工確認」。
- [x] 「尚未收回」在確認視窗即提示「未收回作廢需由管理員確認後才會送出」。
- [x] 「上傳問題」新增「人工確認」狀態與「紙本作廢確認」類型；人工確認不能用一般「標記已解決」直接略過。
- [x] 只有啟用中的 `ADMIN` / `SUPER_ADMIN` 可對人工確認執行「確認送出作廢」或「取消退回」，且底層會再次驗證管理員帳密與角色，不只依賴 UI。
- [x] 管理員批准後重新走既有 AMEGO fresh query／pending／防重核心；`CancelReason` 保留原申請員工編號，不改成批准主管編號。
- [x] 管理員取消退回時不呼叫 AMEGO、發票維持「已開立」；若作廢已送出或已進入遠端待確認則禁止取消。
- [x] 人工確認可跨程式重啟保存原申請員工編號、原因與提出時間，不保存密碼；處理完成後移除暫存資料，不建立永久作廢 audit。
- [x] 人工確認依公司統編與 test/prod 環境隔離。
- [x] Windows CI 已涵蓋確認視窗 smoke、原作廢核心與員工作廢 workflow 安全測試。
