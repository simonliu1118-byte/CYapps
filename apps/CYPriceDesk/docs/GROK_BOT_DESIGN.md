# 價格觀測室 × Grok Bot：建檔補完與候選規格判讀

**狀態：設計稿（使用者 2026-11-27 定方向）。** 本文件只描述需求與設計，不是規則來源。試點商品為 3M 紙膠 **1530-1、1 吋、12 捲／盒**。

## 定位

程式能搜尋、能抓到候選，但辨識不了規格：同一商品頁有多個選項（半吋／1 吋、12 入／24 入）、標題沒寫包裝、酷澎只拿得到飛比摘要。Grok Bot 用它的瀏覽器補上這一步。

- **Grok 不自己搜尋。** 候選一律由現有查價流程產生（fetcher 查 momo、飛比蝦皮／酷澎 → `src/grouping.js` 自動分組 → `latest_candidates`）。
- Grok 只做兩件事：
  1. **建檔補完**：使用者給條件，Grok 補齊「新增追蹤商品」視窗的欄位，尤其是查詢關鍵字。
  2. **候選規格判讀**：對程式找到的候選，進商品頁選規格、讀出該選項的價格，回填判讀與依據。
- Grok 回填的一律是**待確認資料**，由使用者同意或修正後才寫入正式資料。正式資料沿用現有的人工判斷（`listing_judgments`）、價格觀測（`price_observations`）、比價與走勢圖（`public/compare.js`），不另建第二套行情或比價。

## 平台範圍

| 平台 | 候選來源 | Grok 做的事 |
| --- | --- | --- |
| momo | fetcher 的 momo 搜尋結果 | 進 momo 商品頁，實際選取規格／入數／組合，讀對應價格 |
| 酷澎 | fetcher 的飛比酷澎結果 | 由候選連結進入酷澎商品頁（不登入），判斷規格與選項價格；頁面打不開就回報受阻，該候選維持飛比參考價 |
| 蝦皮 | fetcher 的飛比蝦皮結果 | **試點不做**。蝦皮需登入，等使用者替 Bot 準備帳號後再加入（見 `TODO.md`） |

## 一、建檔補完

使用者在「新增追蹤商品」視窗只填條件，按「交給 Grok 補完」。

- **條件**：一段自由文字即可，例如「3M 紙膠 1530-1，1 吋，一盒 12 捲，以盒賣」；已填的欄位一併送出。
- **Grok 補完的欄位**：名稱、型號、規格屬性（`名稱=內容`）、包裝數量、包裝單位、查詢關鍵字，以及進階的個別來源關鍵字（momo、飛比）。
- **不由 Grok 填**：我的售價、我的商品連結、CY Web 品號、是否啟用定期查價。
- **關鍵字**：Grok 可以實際在 momo／飛比試搜，確認關鍵字找得到目標商品，並附上試搜筆數與理由。
- **回到視窗**：補完結果填回視窗，Grok 改過的欄位要標示出來，並附判讀依據。使用者檢查、修改後按「儲存」，才建立追蹤商品；寫入者是按儲存的人。
- **條件互相矛盾時**：例如文字寫 1530-1、照片是 1530-0，Grok 不自行決定，在補完結果提出問題，由使用者在視窗裡選定。

商品照片可幫助辨識，但需要新的檔案儲存資源（R2）；試點先只用文字條件，照片列為後續項目。

## 二、候選規格判讀

### 派工

- 時機：每輪查價（排程或「立即查價」）完成後，可在商品詳情或待確認頁按「交給 Grok 判讀」。
- 範圍：預設為該商品當輪「待確認」與「其他包裝」的 momo、酷澎候選；也可以勾選特定候選。已有人工判斷且標題未變的候選不送。
- 任務會固定本輪使用的商品條件（型號、規格屬性、包裝數量與單位）和候選清單。商品條件之後若被修改，舊任務的回填一律標為過期，不能寫入。

### Grok 的判讀

以「平台、賣家、原商品、實際銷售選項」為一個判讀單位。

- **momo**：同頁有多個選項時，必須實際選取，記錄價格對應哪個選項。
- **酷澎**：由候選連結進入，核對實際賣家、規格、選項與價格。只看得到第三方摘要時標為證據不足。
- **資訊不足**：賣場只寫「12 入」看不出原盒或散裝，先看選項、說明與圖片；仍無法判斷就標「證據不足」，繼續下一筆，不要求使用者替賣家猜。
- **平台受阻**：遇登入牆、驗證碼或頁面讀不到，回報平台與原因，其他候選照常交回。

判讀結果對應現有的人工判斷語意：

| Grok 判讀 | 對應 `listing_judgments.verdict` | 說明 |
| --- | --- | --- |
| 同規格（單盒） | `same` | 與追蹤商品型號、規格、包裝都一致 |
| 其他包裝（單捲、多盒組、散裝） | `other_package`，附 `package_quantity`／`package_unit` | 價格照現有規則只供參考 |
| 不同規格／不是同一商品 | `not_same` | |
| 證據不足 | 不寫入 | 留在待確認，由人判斷 |

單捲換算、多盒平均每盒等計算若需要，放在 `public/compare.js`，不在 Grok 端或另寫一套。

### 回填格式（示例）

```json
{
  "taskId": "task-example-001",
  "taskVersion": 1,
  "candidate": { "source": "momo", "listingKey": "listing-example" },
  "selectedOption": "白色 1 吋／12 捲盒裝",
  "observedSpec": { "model": "1530-1", "attributes": { "尺寸": "1吋" }, "packageQuantity": 12, "packageUnit": "捲" },
  "verdict": "same",
  "price": 240,
  "priceCondition": "公開售價",
  "seller": "範例賣家",
  "productUrl": "https://example.invalid/product/123",
  "checkedAt": "2026-11-27T10:30:00+08:00",
  "evidence": "已選取 1 吋盒裝；規格欄列出 1530-1，選取後顯示此價。"
}
```

缺少的規格或價格填 `null` 並在 `evidence` 寫原因。回填一定對應任務內的既有候選；不在任務內的候選一律拒收。

### 複審

在現有待確認頁與商品詳情的候選表，Grok 已判讀的列顯示判讀、選項、價格、證據與網址，操作為：

| 操作 | 效果 |
| --- | --- |
| 同意 | 依判讀寫入 `listing_judgments`；判為同規格且有價格時，以 Grok 讀到的選項價格寫入 `price_observations` |
| 修正並採用 | 在 Grok 判讀上改錯的欄位後寫入；保存原判讀與人工結果 |
| 請 Grok 再查 | 附具體原因，例如「請確認此價是否對應 1 吋選項」，只重查該筆 |
| 刪除 | 見下節 |

寫入正式資料的操作者是按下操作的使用者（CYID principal），沿用現有 audit。

### 刪除只針對當輪候選

在待確認表格的「同規格／其他包裝／不是同一商品」後加上「刪除」，商品詳情的候選表同樣適用。用於停售、下架或本輪不需要保留的商品。

- 不保存刪除名單、不建立排除規則，也不轉成人工判斷；下一輪查價照常從搜尋結果建立候選，來源再次回傳就會重新出現。
- 以候選識別加上當輪版本定位，不依標題或價格批次刪除；清單已換成新一輪時提示重新整理。
- 舊候選晚到的 Grok 回填只能更新仍存在的列，不能把已刪除的列重新插入。
- 不刪除歷史價格觀測。
- 現有 `latest_candidates` 每輪整批覆蓋、沒有輪次欄位，需要新增 migration 記錄當輪版本。

## 三、任務與 webhook

1. 價格觀測室建立任務（建檔補完或候選判讀），頁面顯示「已派工」。
2. Worker 以 HTTPS POST 呼叫 Grok routine 的 webhook，帶該 routine 的 Bearer 金鑰（Worker secret）。webhook 只帶事件與任務編號，不帶商品資料。
3. Grok 以專屬機器憑證向價格觀測室領取任務內容，回報進度、提問與結果。頁面顯示「判讀中」，依平台分別追蹤。
4. 完成後分別顯示「完成」「部分完成」或「受阻」；人工複審進度另外顯示。
5. 重送同一事件沿用原 `eventId`，不重開任務。派工失敗顯示未送達，保留任務供重送。

```json
{ "schemaVersion": 1, "event": "pricedesk.task.ready", "eventId": "evt-example-001", "taskId": "task-example-001", "taskVersion": 1 }
```

| 事件 | 附加欄位 | 用途 |
| --- | --- | --- |
| `pricedesk.task.ready` | — | 首次派工 |
| `pricedesk.question.answered` | `questionId` | 使用者回答後續查 |
| `pricedesk.review.recheck` | `resultId` | 「請 Grok 再查」 |

### 任務接口（擬定）

基底路徑 `/api/grok/tasks/{taskId}`，只接受 Grok 機器憑證且限該任務。

| 方法與路徑 | 內容 |
| --- | --- |
| GET 基底路徑 | 任務類型、商品條件、候選清單（來源、識別、連結）、任務版本、已有問答 |
| POST `/progress` | 平台、狀態；結束時附受阻或部分完成原因 |
| POST `/questions` | 問題、可選答案、受影響的欄位或候選 |
| PUT `/draft` | 建檔補完的欄位、試搜結果與依據 |
| PUT `/results/{resultId}` | 單一候選的判讀結果（上節格式），以任務版本與結果識別去重 |

機器回填只寫入任務與待確認資料表，不直接寫 `tracked_products`、`listing_judgments`、`price_observations`。

## 需要先處理的治理事項

- **機器身分寫入**：`PROJECT_RULES.md` §4 規定寫入操作者只取自 CYID principal。Grok 回填雖然只進待確認資料，仍屬寫入，以 governance 2.3.67（CYapps #650）在 `PROJECT_RULES.md` 寫明：Grok 機器憑證只能寫任務與待確認資料表、稽核記錄方式、憑證保管與輪替。
- **用量上限**：依使用者 2026-11-27 指示，試點先不設上限，測試流程跑通後再定（共通規則 §11.3 要求排程與重試有上限，正式啟用前必須補上）。
- **Grok Bot 能力**：瀏覽器操作已由使用者手動試 1530-1 確認（2026-11-27：可開 momo 與酷澎商品頁、選規格、讀到價格）。webhook 觸發與帶憑證呼叫價格觀測室 API 尚未實測（官方說明：[Grok Bot webhooks](https://docs.x.ai/grok-bot/skills-routines-and-automations#webhooks)），實作第一步先打通。

## 試點驗收

1. 只輸入「3M 紙膠 1530-1，1 吋，一盒 12 捲，以盒賣」，Grok 補完名稱、型號、規格屬性、包裝、關鍵字；使用者修改後儲存，建立者為使用者。
2. 條件矛盾時，問題出現在視窗，使用者選定後補完繼續。
3. 立即查價後送 Grok 判讀：momo 同頁含半吋與 1 吋時，回填被選取的規格與對應價格；酷澎由飛比連結進入商品頁判讀；打不開時回報受阻，其他候選照常交回。
4. 同意一筆同規格、一筆其他包裝、一筆不是同一商品：分別寫入對應的人工判斷，同規格價格進入比價與走勢圖；未複審的結果不進入任何統計。
5. 修改追蹤商品的規格後，舊任務的晚到回填被拒收。
6. 18 筆待確認刪除其中 1 筆，列表與徽章顯示 17；同名鄰列、歷史價格不受影響。下一輪查價：來源未回傳時維持缺席，再次回傳則重新入列。
7. 測試以假 Grok 回填與假 fetcher 執行，不連線 momo、飛比、酷澎或 Grok。
