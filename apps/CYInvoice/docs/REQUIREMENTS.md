# CYInvoice 功能基準

## V2 現行功能基準

- Windows 10/11 x64 可攜式 GUI EXE，免安裝其他執行環境。
- 手動開立電子發票。
- MO店+ 原始加密 Excel 匯入、確認及批次開立。
- MO店+ 原始 `OrderExport` 依完整欄名辨識，不依檔名或固定欄位位置；受密碼保護的 `.xls` 由 Excel COM 唯讀開啟，全程只在記憶體轉換，不建立中介 Excel。
- MO店+ 每列商品金額以官方 `開立發票金額_依品項(若您是自行開立發票，請依此金額開立予消費者)` 為最高準則；不得用商品售價、平台淨入帳或自行折扣計算覆蓋。訂單最後以官方 `開立發票金額加總(...)` 核對，只有兩個官方欄位彼此矛盾時才停止。
- MO店+ 客人支付運費與商品滿額免運費各加入一次；平台補貼運費只有在官方訂單總額需要該金額才能相符時才列為運費補貼，預估平台代扣運費不得計入消費者發票。
- MO店+ 原始檔的「收件人姓名」對應買方名稱；品名由「商品名稱＋規格1＋規格2」依非空欄位組成。只有「發票開立統編」是買方統編，原始檔另列的店家統編不得誤用。
- 有買方統編的 MO店+ 訂單一律紙本；沒有買方統編的一律使用光貿會員載具，載具顯碼與隱碼均為 `motmp_原始訂單編號`，並將載具資料保存在本機發票紀錄。
- MO店+、酷澎與鼎新 ERP 的來源解析器只負責依各自表頭轉成共用訂單資料；選擇 Excel 後全部立即開啟同一套「開立發票匯入確認」視窗，於該視窗顯示解析、統編查詢及開立進度，不得先返回主視窗等待。確認表約顯示 10 列並可捲動，「開立」使用原生 checkbox；未勾選、取消單張或取消整批都不得送出。
- 公司統編名稱固定依「本機人工記憶 → 光貿統編 API → API 正常回覆但查無名稱才人工輸入」處理。光貿 code 99 的統編業務驗證回覆或成功但沒有相符資料，代表 API 可正常查詢，右上狀態保持正常並提醒「查無此統一編號，請再次確認或自行輸入買方名稱。」連線、逾時、授權、簽章或其他技術錯誤才是 API 異常，且不得誤當查無名稱；人工名稱只在該張發票確定成功後保存，明確失敗、取消、未勾選或結果仍不明時不保存，結果不明日後查詢確認已開立才保存。
- MO 官方開立金額是含稅價。公司發票的含稅 MO 明細使用 DetailVat=1，確認畫面及 API 將官方含稅總額拆為未稅應稅銷售額與 5% 稅額；例如官方總額 1014 必須為銷售額 966、稅額 48、總額 1014，不得把 966 當成新的發票總額。
- 光貿測試環境是跨公司共用測試池。依最新定案，API `OrderId` 保留原始訂單編號；其餘可識別客戶資料仍須去識別化：BuyerName 固定為「測試消費者」，B2B 真實買方統編改用光貿官方文件公開的測試買方統編，地址、電話、Email、捐贈碼、主備註及明細備註清空，商品名稱依序改為「測試商品 N」，會員載具顯碼與隱碼均改為不含訂單資訊的固定測試 Email。本機確認與紀錄保留原始資料，正式環境不得套用這些替換。
- 酷澎已寄出 DeliveryList 格式 .xlsx 匯入、確認及批次開立；辨識依欄名與必要欄位組合，不依檔名或欄位位置。
- 鼎新 ERP 必須沿用相同匯入確認流程；在取得實際銷貨單樣本及欄位對照前，解析器必須明確停止並保證不送出，禁止猜測表頭或金額。
- 已開立發票清單、條件查詢、狀態重新整理及防重複開票；雙擊實際資料列開啟該筆本機紀錄的原生唯讀詳細資訊，開啟詳細資訊本身不發 API、不得改變紀錄或提供重送捷徑。只有使用者再按「檢視 PDF」才可執行 PDF API。
- 紙本發票只要同環境、已開立且有發票號碼，即可直接透過 `/json/invoice_file` 嘗試取得官方 PDF，不以上傳狀態 `99` 為前置條件；一般消費者按「檢視 PDF」後固定使用 `download_style=0`，公司統編按下後顯示 0、1、2、3、5 五種官方版型選單，選擇後才取得 PDF。若光貿尚未提供檔案，應提示稍後再試，不得改變發票或上傳狀態。
- PDF Cache 依環境、日期、發票號碼及 `download_style` 隔離；同日重複檢視沿用有效 Cache，隔日重新取得，損壞或非 PDF 內容不得沿用。官方短效 `file_url` 只接受光貿 HTTPS 網域。
- PDF Viewer 使用 WebView2 內嵌檢視並由 Edge PDF Viewer 原生工具列提供縮放、下載與列印，不另外顯示 CYInvoice 自製工具列；關閉視窗必須釋放 WebView2 控制項，一般消費者不得切換版型，公司各版型 Cache 不得互相覆蓋。
- 訂單編號可自動產生或自訂；買方資料可選一般消費者或公司統編，兩者為獨立選項群組。
- 商品明細必須使用原生 `SysListView32` 真正表格，預設完整顯示 5 列、最多 50 列；只允許垂直捲動，永久保留系統垂直 scrollbar 槽，欄寬不得產生橫向捲軸。品名、數量、單價以表格內暫時編輯框編輯，課稅別及金額唯讀；金額欄必須以灰底清楚表達不可輸入，不得以多個永久 Edit 控制項疊在格線上模擬表格。單價編輯時維持純數字，Enter、Tab 或離開儲存格後才以千分位顯示；發票各金額顯示與金額總計也使用千分位，總計三個數值右緣對齊。
- 新增明細不得預先檢查目前列，任何狀態都可繼續新增；只有最後開立時驗證。完全空白列自動移除，部分填寫的列則必須提示使用者補齊。
- 商品品名、數量、單價第一次取得焦點時全選；Enter 依品名 → 數量 → 單價移動。單價按 Enter 後，若已有下一筆實際明細列就移至該列品名；若目前是最後一筆則自動新增一列並移至新品名欄。Tab 保留既有鍵盤導覽，不因本規則改變。
- 發票總備註最多 200 字。
- 同來源＋原始平台訂單編號已有已開立、結果不明或其他未明確可重開狀態時，禁止再次開立。
- 明確失敗或已作廢才允許重新開立。
- 光貿查得到的公司名稱不存本機；只有查詢成功但名稱空白、人工輸入且成功開票後才保存。
- 公司統編輸入完整 8 碼後自動查詢公司名稱；先查本機記憶，再查光貿 API。查詢失敗不得視為查無名稱，也不得觸發人工名稱記憶。
- `SentAt`（送出時間）不可被後續狀態查詢覆蓋；開立時間與最後狀態查詢時間分離。
- 一般 LOG 與 ERROR LOG 分開保存。
- 全新 `Data/settings.json` 或安全設定不完整時，必須以不可略過的窄版首次設定視窗建立 MO店+ Excel 密碼與管理密碼；文字背景保持透明、字級小於主介面，輸入框不得過大。Tab／Enter 都依「MO店+ Excel 密碼 → 管理密碼 → 再次輸入管理密碼」前進，只有最後一欄 Enter 才直接儲存。
- 首次設定完成後才可進入主程式；首次環境固定為光貿測試環境，正式公司資料須再由獨立設定視窗解鎖輸入。
- 已存在的 MO 密碼必須能由目前 Windows 使用者以 DPAPI 解密；若資料夾來自另一台電腦或其他帳號而無法解密，保留原設定並停止啟動，不自動覆蓋。
- 主視窗一般狀態固定使用預設尺寸，只允許最大化、還原與最小化；最大化與還原時必須重新配置控制項與清單欄寬。
- 已開立發票清單預設日期為本月第一日至今天。
- 酷澎以「應開立予買家之發票金額」作為買家發票明細金額；「應開立予酷澎之發票金額」不得計入。
- 一般消費者固定使用含稅明細；畫面拆分顯示未稅銷售額與稅額，送 API 時 BuyerIdentifier=`0000000000`、BuyerName=`消費者`，並依光貿規則 TaxAmount=0、DetailVat=1。
- 公司統編可選含稅或未稅；未稅明細使用 DetailVat=0，SalesAmount 為應稅明細加總、TaxAmount 為 SalesAmount×5% 四捨五入、TotalAmount 為兩者合計。
- 公司發票已有商品明細時切換含稅／未稅，所有單價自動換算並採固定小數點後 7 位運算；不得使用二進位浮點數累積誤差。驗收基準為含稅 `200` → 未稅 `190.4761905` → 含稅 `200`。
- 啟動、設定儲存及 API 操作後，以光貿統編查詢 API 做唯讀健康檢查；查詢中灰色、成功綠色、失敗紅色。已收到且可解析的業務驗證回覆（例如測試統編的 code 99 格式錯誤）代表 API 可連線，仍視為正常；連線、逾時、授權、簽章、帳號或服務錯誤才視為異常。異常原因以更小的灰字放在狀態下方，使用單一 10 秒計時器重試，且同一時間只能有一個健康檢查。測試環境查測試統編，正式環境查設定的公司統編。
- 光貿發票查詢須相容官方物件格式，以及既有環境實際回傳的一層或巢狀陣列格式；重新整理只更新狀態，不得重送發票或覆寫原開立時間。
- 光貿回查不能只憑 `OrderId` 宣稱開立成功；必須唯一命中同環境、同 API OrderId，並核對發票號碼、未稅銷售額、稅額、總額、DetailVat 與未作廢狀態。零筆、多筆、欄位不一致、資料變更中或已作廢皆不得當成本次成功。
- 已作廢訂單可重新開立，但送至光貿的 API OrderId 必須使用可追蹤的新尾碼 `-R2`、`-R3`；本機仍保留原始平台訂單編號，不以舊發票誤認新發票。
- 同一時間只允許一個 CYInvoice 程序；同一程序中的開立流程亦須序列化「防重檢查 → 建立待處理紀錄 → 送出」，避免多視窗或重複點擊穿透防重規則。
- 光貿已回覆成功、但本機紀錄保存失敗時，必須明確顯示「遠端已開立／本機保存失敗」，保留可回查識別資料並禁止當成一般失敗重新送出。
- 所有可能等待網路或整批開立的操作必須在背景執行並設逾時；UI 執行緒只負責接收結果、更新控制項及依序啟動下一張，不得在 Win32 window procedure 內同步等待 API。
- `.xlsx` 解析須依 workbook relationship 找到實際第一張工作表，並限制 ZIP 展開大小、列數及欄數；Excel COM 開檔必須唯讀、停用巨集、外部連結更新、事件及提示，且失敗時不得退回不安全模式。
- 新管理密碼使用 PBKDF2-HMAC-SHA256（至少 210,000 次）保存；既有舊雜湊仍可驗證並於更新後升級。管理密碼錯誤須節流，避免無限制高速嘗試。
- 主畫面的開立發票與已開立發票清單維持一致、可讀的 Windows UI 字體；不得以假的標題蓋住 GroupBox 框線。三個匯入動作使用明確的圓角按鈕，與含稅／未稅選取高亮區分。兩個主頁籤的選中與未選中狀態必須有明顯差異。
- 商品與已開立發票清單使用原生 WinForms `ListView`／Windows Header／系統垂直 scrollbar；儲存格背景、文字、斑馬紋與連續格線由單一核准的 owner-draw subitem 路徑繪製，不得混入第二套整列手工表格或重複狀態路徑。商品清單及已開立清單的整個可見表格區均須維持逐列斑馬紋；已開立清單不足一頁時以不可操作的 UI 空白列補滿，不得寫入本機發票紀錄。兩個清單都永久保留系統垂直 scrollbar 槽，最後實際欄位必須緊接該槽且不得產生水平 scrollbar。已開立清單的來源欄固定足以完整顯示 `MO店+`、`好賣+`、`iOPEN`，訂單編號固定足以顯示 15 碼，統編欄固定足以完整顯示 8 碼統編及既有一般消費者值 `0000000000`；三欄不得因視窗寬度縮減而被壓縮。
- 設定是頁籤列右上角的一般按鈕，按下後開啟獨立設定視窗。每次開啟只顯示管理密碼驗證，驗證成功後才顯示設定內容；取消或關閉視窗即重新鎖定，下次開啟必須再次驗證。正式公司設定的標籤使用 `統編` 與 `App Key`，兩者標籤左緣及輸入框左緣分別對齊，App Key 使用獨立完整一列。
- 一般消費者模式下，統一編號及買方名稱欄位必須停用並以灰底、灰字清楚呈現；公司統編模式才恢復白底可輸入。
- 已開立發票清單的「重新整理狀態」只更新發票資料與按鈕本身的進度，不得把右上角 API 健康燈改成查詢中。
- 發票詳細資訊使用緊湊三欄摘要；空白錯誤訊息與總備註不保留高度，商品明細使用剩餘主要空間，底部只保留置中的「檢視 PDF」與「關閉」。
- 光貿回覆 code 15 時，使用官方 `/json/time` 取得伺服器 Unix timestamp 校正簽章時間，原 API 僅自動重試一次，不修改 Windows 系統時間。
- 發行 ZIP 解壓後根目錄包含 `CYInvoice.exe`、當版唯一 `V版本號.txt` 及 `使用說明.txt`；不得有 `Version` 資料夾或 `todo.txt`。

## V2 後續開發計畫

- 會員載具開立成功顯示發票號碼、開立時間、來源、訂單編號、金額、交付方式、發票狀態與系統資訊。
- 會員載具檢視必須明確標示「此為發票模擬示意圖，非真實發票」。
- 作廢必須驗證員工帳號、密碼及作廢原因；員工密碼只保存雜湊。
- 只有已開立、有發票號碼、上傳完成且未跨期的發票可作廢。
- 作廢列使用灰字及刪除線，但上傳完成狀態仍獨立顯示綠燈。
- 網路逾時或傳輸錯誤時先以 OrderId 回查；無法確認則標記結果不明並鎖定重開。
- 註銷重傳不實作，低頻需求由光貿網站處理。

## 後續範圍

- 酷澎未出貨、公司統編、數量大於 1、折扣等其他實際格式樣本驗證。
- 鼎新 ERP 銷貨單轉檔。
- 折讓功能（另行討論後實作）。
