## 3. 折讓功能

### 3.1 暫行人工流程

在 AMEGO 折讓 API 正式串接前，先提供單純、可追蹤的人工處理流程；這是經使用者核准的暫時例外，目的在避免現在先做一套 API 整合、雲端化時又重做一次。

預定流程：

1. 從發票詳細資料按「折讓」；是否可提出折讓，以 AMEGO 官方可操作條件與 fresh `invoice_query` 的官方狀態為準，不自行用月份或其他本機推測取代官方判斷。
2. 員工輸入折讓原因、**含稅折讓總額**、員工編號與員工密碼。
3. 驗證員工存在、啟用且密碼正確；驗證失敗不得建立待處理事項。
4. 驗證成功後**不呼叫 AMEGO 折讓 API**，改在「上傳問題」建立一筆人工待辦。
5. 人工待辦類型使用「折讓人工處理」，沿用既有 `InvoiceSyncIssue`／`ResolvedUtc` 資料模型；真正的申請資料保存於發票既有延伸資料，至少包含原申請員工編號、折讓原因、含稅折讓總額與提出時間，不保存員工密碼。
6. 同一張發票已有未解決的「折讓人工處理」時不得重複新增第二筆；待辦完成或取消退回後，未來仍可依 AMEGO 官方規則再次提出新的折讓申請。
7. 「折讓人工處理」沿用紙本未收回作廢的**同一個上傳問題／人工確認入口**。選取折讓待辦時提供「已解決」與「取消退回」兩個動作；兩者都必須重新驗證啟用中的 ADMIN／SUPER_ADMIN，不另做折讓專用管理員登入機制。
8. 管理員進入折讓人工處理後，顯示必要的原發票資料、申請員工、申請時間、折讓原因與含稅折讓總額。管理員自行至光貿網站完成實際折讓後，回到 CYInvoice 按「已解決」；底層直接沿用既有 `Resolve()`／`ResolvedUtc` 結案，不新增第二套完成狀態。
9. 若管理員決定不處理，按「取消退回」；同樣走既有人工確認的管理員驗證與結案路徑，清除該筆折讓人工申請資料並 resolve 對應 issue，且**不對光貿執行任何折讓操作**。
10. `invoice_query` 的折讓資訊解析納入既有共用 QueryResult／官方資料更新流程；任何既有流程執行 `invoice_query` 時都使用同一套解析。
11. 折讓補查沿用現有「作廢 pending 超出 recent list 覆蓋時單筆 query 補洞」的**同一種 post-list reconciliation 機制**：啟動、5 分鐘、手動與每日同步仍先走既有同步；對仍未結案、而 `invoice_list` 無法提供足夠折讓資訊的發票，再以既有 `invoice_query` 單筆補查。只查這些待辦中的發票，不掃描所有發票、不建立折讓專用排程。由於 `invoice_list` 本身不足以判斷 allowance，這裡沿用的是「單筆補洞機制」，不是硬套必須超過 3 天才可 query 的條件。
12. Query 補查只負責更新光貿官方折讓資料，**不因 `allowance[]` 非空就自動 resolve 人工待辦**，避免把原本已存在的舊折讓誤認為本次申請已完成；人工待辦仍由管理員明確按「已解決」或「取消退回」結案。

實作前需注意：

- 折讓人工處理與紙本未收回作廢共用「人工確認」入口、管理員驗證與 issue 結案模型，但保留不同 `IssueType` 與申請資料，避免兩種業務語意混在一起。
- 目前 `invoice_query` 的 `QueryResult` 尚未解析 allowance 資訊；暫行流程需補上既有 query contract/parser 的最小必要欄位，但仍不串 `g0401`／`g0501`／`allowance_query` 等折讓專用 API。
- 折讓不得改寫既有發票主狀態為「已折讓」；發票仍依官方規則維持已開立／已作廢等主狀態，折讓資訊作為獨立官方資訊處理。
- 目前人工版「已解決」只是管理員確認已在光貿網站處理完成。未來正式串接折讓 API 時，保留同一個待辦入口與管理員確認畫面，把「已解決」替換為「確認送出」；只有 API／官方狀態確認後才 resolve，避免重做整套流程。

暫行流程不做：

- 不由 CYInvoice 呼叫折讓開立／作廢折讓 API。
- 不在本機模擬光貿已完成折讓。
- 不自行產生官方折讓單號。
- 不另建 allowance 專用同步排程、第二套 issue 狀態模型或第二套結案流程。
