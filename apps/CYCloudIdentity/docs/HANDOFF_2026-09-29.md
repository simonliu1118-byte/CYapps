## 2. Finalized product model

CYCloud Identity owns:

- Workspace identity/lifecycle;
- Employee identity and lifecycle;
- credentials;
- exactly three Workspace roles: `SUPER_ADMIN`, `ADMIN`, `USER`;
- protected Super Admin authority pointer;
- `Identity Admin` capability on ADMIN;
- Application Registry and entry Access;
- Identity sessions;
- Email OTP/recovery;
- Identity audit events.

CYID does not own universal per-App module/business permissions.

### Super Admin

- exactly one per active Workspace;
- protected authority pointer, not an ordinary mutable role;
- cannot be demoted/disabled/deleted by another Employee;
- automatically has all Workspace-enabled App access;
- only authority that can grant/revoke Identity Admin capability, transfer Super Admin, and manage Workspace Recovery/security-core/OTP policy.

### Admin

- normal Workspace administrator;
- can manage ordinary USER lifecycle;
- has no Application Access or CY Web Module Access configuration capability.

### Identity Admin

- ADMIN + special Identity-management capability; not a fourth role;
- can create USER or ADMIN;
- can perform USER <-> ADMIN;
- can manage App Access for USER/ADMIN/other Identity Admin accounts, except its own;
- can manage CY Web Module Access through CY Web, except its own;
- can force Email recovery for activated Employees;
- cannot grant/revoke Identity Admin capability, demote another Identity Admin, or touch Super Admin protected state.

### User

- ordinary Employee role;
- App-local detailed permission model primarily applies here.

Future HR note: if a non-ADMIN HR role later needs Identity lifecycle authority, decompose narrower Identity capabilities then; do not add a fourth role now.

## 3. CY Web special case

CY Web is both the shared account shell and a multi-module business application.

- every valid Employee has CY Web entry access locked TRUE;
- this remains true even if the Employee has zero business-module access;
- users must be able to enter CY Web to manage their own account;
- Super Admin has all CY Web modules automatically;
- Identity Admin / Super Admin can manage eligible Employee CY Web Module Access;
- normal Admin cannot manage Module Access;
- an Admin with a module Access has full administration authority in that module;
- module authority stays in CY Web, not CYID.

## 4. Other Application Access

Role and App Access are independent.

- new Employee creation does not auto-grant ordinary Apps;
- Access is configured after creation;
- role changes preserve current Access;
- normal Admin cannot configure Access;
- Identity Admin can configure USER / ADMIN / other Identity Admin App Access except its own;
- Super Admin can configure eligible Employee Access and has automatic access to every Workspace-enabled App;
- consumer role is direct 1:1: CYID SUPER_ADMIN -> App SUPER_ADMIN, ADMIN -> ADMIN, USER -> USER.

The legacy Group-derived `applicationRoleKey` is being retired.

## 5. Employee creation and activation email

Finalized create rule:

- normal Admin may create USER only;
- Identity Admin / Super Admin may create USER or ADMIN directly;
- role is chosen in the create form;
- Identity Admin capability itself is never granted during create.

Finalized activation behavior:

1. create the pending Employee;
2. immediately send the first activation email;
3. the email contains a direct link that opens the CY Web activation flow;
4. the link itself is not authentication and does not bypass OTP/Email verification/first-password setup;
5. Employee completes Email verification + first password;
6. account becomes enabled.

Pending row actions:

```text
編輯 | 重寄啟用信 | 刪除
```

If delivery fails, keep the pending Employee and show a send-failure/resend path. Do not roll back account creation.

Important current-runtime fact: `0.1.14 handleCreateEmployee()` does **not** send mail. The provider currently sends activation OTP only when the Employee explicitly starts activation. Therefore a newly created Employee causing no Brevo event is expected under the current code and is not evidence that Brevo itself failed.

## 6. Employee lifecycle / deletion

Consumer-visible states:

- 尚未驗證／待啟用;
- 啟用;
- 停用;
- 啟用 · Email 待驗證 (after authorized Email recovery).

Only never-activated Employees may be physically deleted. Activated Employees are retained and later disabled/re-enabled so Audit/history references remain valid.

## 7. Forced Email recovery

Identity Admin / Super Admin may change an activated Employee's Email if the old Email is banned/lost/unusable.

After forced Email change:

- account remains activated;
- password remains unchanged;
- new Email is unverified;
- current sessions are revoked;
- verification can be resent;
- account does not revert to first-time pending activation.

Normal Admin cannot use this path.

## 8. Session / immediate authorization behavior

Authorization changes must take effect server-side:

- disable Employee -> all sessions invalid;
- role change -> existing sessions invalid/re-resolved under new role;
- App Access revoke -> that App can no longer authorize the session;
- forced Email recovery -> Employee sessions revoked;
- CY Web Module Access change -> subsequent protected CY Web requests enforce the new access.

Browser UI is never the authority source.
