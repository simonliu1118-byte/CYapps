## 2. Architecture that is already fixed

CYCloud Identity Worker + Identity D1 is the authority for Workspace, Employee, credentials, extensible Identity Groups/memberships, Application Registry/Access, sessions, Email OTP/recovery, the protected Workspace Super Admin pointer/Recovery Email, Super Admin transfer, coarse per-Application compatibility role, and Identity audit events.

CY Web only renders management UI and proxies through its private Identity Service Binding. It must not duplicate credential/session/OTP/Group authority in its business D1.

Consumer-facing terminology is **超級管理員 (Super Admin)**. Stable contract/storage fields such as `isWorkspaceSuperAdmin`, `superAdminEmployeeId` and `super_admin_employee_id` remain unchanged. Super Admin is not an ordinary Group or editable role enum.

## 3. Authentication and credential state

Implemented and deployed:

- application-aware `POST /v1/identity/login`
- `POST /v1/identity/session/resolve`
- `POST /v1/identity/logout`
- opaque session token; D1 stores only the token hash
- login/session resolve re-check current Employee/Workspace/access/credential revision
- new credentials use `scrypt`
- bounded legacy `pbkdf2-sha256` verify remains compatibility-only
- password boundary is 8–16 Unicode characters
- development session TTL currently resolves to the accepted 8-hour behavior
- Cloudflare Rate Limit binding protects login

CY Web browser/runtime acceptance already passed for password login, authenticated navigation, F5 session resolve, logout, post-logout F5, and a provider-invalid session. Literal expired-session evidence remains separate and outstanding.

## 4. Email / OTP / recovery state

Implemented:

- provider-neutral Email Sender with Brevo/Resend adapters
- runtime-only provider credentials
- 6-digit Email OTP; HMAC digest; purpose isolation; one-time consumption
- default validity 10 minutes
- Workspace-editable resend cooldown / max attempts / hourly Email+purpose cap / daily Workspace Email cap
- server-side bounds
- global/provider daily ceiling remains runtime-only and cannot be raised by a Workspace

Established defaults: resend 60 seconds, max verify attempts 5, Email+purpose/hour 5, Workspace/day 100 unless the lower system ceiling wins.

OTP security settings are rendered only when `isWorkspaceSuperAdmin=true`; all other Employees see no management entry/control. Backend authorization remains the security boundary.

Implemented self-service: own password change, own Email change via current-password re-auth + Email OTP, password recovery via Email OTP, and session invalidation through credential version change.

## 5. Employee lifecycle and Super Admin

Employee lifecycle is explicitly three-state from the consumer perspective:

1. **尚未驗證／待啟用** — Super Admin created the Employee, Email not verified, credential absent, `enabled=0`; no admin-side enable action is valid yet.
2. **啟用** — Employee completed Email OTP and first-password setup; Email is verified and account is enabled.
3. **停用** — an already activated Employee was later disabled; this is distinct from first-time pending activation and can be re-enabled subject to authorization.

CYCloud Identity `0.1.14` adds a protected DELETE endpoint for pending first-time Employees:

- requires Workspace Super Admin authority;
- allows deletion only while Email is unverified, credential is absent and `enabled=0`;
- rejects deletion after activation;
- rejects deletion of the current Super Admin;
- removes pending activation OTP challenges for the deleted account;
- writes an Identity audit event;
- existing schema protection/cascades remain authoritative; no migration was required.

Super Admin transfer remains current-password re-auth + Email OTP. Completion moves the authority pointer and Recovery Email and revokes previous Super Admin sessions. The current Super Admin cannot be directly disabled or deleted before transfer.

CY Web `0.1.51` moves the transfer entry into the current Super Admin Employee row. If no enabled/verified target exists the transfer button is disabled; otherwise it opens a modal for target selection, password re-auth and OTP confirmation. The previous standalone authority panel is removed.

## 6. Groups, Application Access and CYInvoice compatibility role

Ordinary Groups remain extensible and data-driven. Access sources are Group Application grants, direct Employee grants and protected Super Admin access.

`USER_ADMIN` effective projection:

- Super Admin => `SUPER_ADMIN`
- any active Group grant with `ADMIN` => `ADMIN`
- otherwise active Group grant with `USER` => `USER`
- otherwise direct Application grant => `USER`
- otherwise no Application access

Ordinary Groups may only set `USER` / `ADMIN`; Groups can never grant `SUPER_ADMIN`. CYInvoice should consume Identity's effective `applicationRoleKey` and remains unmodified in this workstream.
