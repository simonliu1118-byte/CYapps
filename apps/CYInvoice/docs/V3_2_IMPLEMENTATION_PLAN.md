### 同機返修與診斷（V3.1.44 Build1／Cloud Source0.9.8）

本輪依使用者指示先收斂同機申請／核准，不切LocalOnly、不變交易owner，跨機協同留下一版處理／驗收。修正Cloud非空清單7欄與Windows6欄不一致，清單與詳情使用原發票／訂單參照，不再把application ID當訂單或刻意隱藏已知號碼。狀態存原sync_state投影，待核准判斷不再依訊息字串；核准出錯依原ID查回一次，不重做核准、create或財務POST。

Cloud保存核准Grant後即回覆已核准／處理中；財務執行沿原coordinator及既有ExecutionContext.waitUntil，背景使用原Grant authority snapshot與既有私有撤權檢查，不保留或延長真人Session／密碼。中斷仍由原runtime/sync恢復。Windows核准請求有界90秒、其他讀取30秒，不再用10秒涵蓋完整送出／查回。這不宣稱已找出舊失敗的實際根因，舊案沒有核准／發號證據時不補造結果。

log沿原IssueDiagnosticLog，新增紀錄放程式同目錄`log`：HTTP請求開始／回覆／失敗、版本／Build、UTC時間、action、application ID、request ID、耗時、HTTP結果、回覆是否到達、後端階段及安全錯誤碼；核准失敗自動按原ID讀診斷並保存安全事件。Cloud核准前段記官方查證、Grant保存及失敗階段至原事件表，失敗分類不再只改文字。每日日誌4MiB輪替，保留一份前段、14天；原單筆問題證據不隨每日清理刪除，舊Data/Logs診斷保留唯讀匯出。缺磁碟／權限明示寫入失敗，不把記錄失敗當交易失敗或自動重送。

log不保存員工密碼、Device Token、公司卡金鑰、姓名／買受人、商品／金額、原始請求或回覆。處理中與上傳問題皆可匯出既有診斷；Cloud取不到時仍能匯出本機證據。新檔案列入忽略與原Source／package保護，撤銷裝置仍沿原清理owner處理，不增加診斷視窗、待辦入口、資料表或排程。

本輪驗收重點為「同機一般員工申請→主管一次核准→原待辦自動處理→官方結果／問題分類」，需使用Build1配套Cloud0.9.8。實際遠端0.9.7維護已完成，不重做；此輪無實際核准／交易。舊單實際失敗原因僅能依原證據界定到核准未持久化，不能宣稱10秒逾時就是根因；完整原單識別與私有診斷不公開。

## 2. 已定案的產品流程

### 2.1 共用入口：「待辦/處理中」與「上傳問題」

2026-10-26最新介面定案：按鈕為「待辦/處理中」，沿原處理中單一清單。沿原RecordsControl、InvoiceWorkQueue及SyncIssuesForm整合「處理中」單一入口，移除獨立「跨機待辦」按鈕／選單，非折讓Cloud工作項目亦從同一入口開啟。恢復原處理中視窗的單一原生清單，待核准與處理中直接並列，不再增加來源頁籤或額外狀態篩選；核准後更新原操作，由原業務owner自動處理，完成後移出，異常仍進既有「上傳問題」。Local／Cloud來源不構成第二個使用者入口，不新增待辦平台或排程。

| 入口 | 收納項目 | 行為 |
| --- | --- | --- |
| 處理中 | 待核准／等待紙本，以及已核准由程式處理、官方等待／上傳／查證 | 顯示原因與最新狀態；需人處理的項目依角色可直接開啟詳情，程式等待的項目自動追蹤 |
| 上傳問題 | 明確失敗、逾時查證後仍無法確認、查無原發票、資料衝突、超限、保存失敗、權限／版本／設定異常 | 顯示具體原因、最後結果、下一步與「匯出問題診斷」，避免只有一句失敗或無效人工分類 |
| 已完成紀錄 | 官方可確認的開立／作廢及已完成處理 | 移出未完成清單，保留申請、核准、API 嘗試、官方結果與處置歷程 |

清單開啟、重新整理與有界分頁不收員工帳密，使用原active CYID Device、Workspace及當前Application access讀最小摘要；不公開來源雜湊、申請人／裝置識別或發票內容。原同一路由的詳情、已封存歷史與人工封存仍須當次管理員驗證，任何寫入仍保留原角色、Device、版次及稽核。詳情入口驗證成功後，該次確認操作沿用輸入，不再次彈窗；一般系統處理中狀態可直接唯讀查看。需人工處理的狀態以紅字呈現，官方／系統等待維持原提示色。共用EmployeeAdminLoginForm統一標題「密碼驗證」，呼叫端只指定需要的角色；帳密錯誤、權限不足或連線問題分別提示並保留驗證窗。

同一操作依目前狀態只出現在適當清單，不能因同時有歷史錯誤而重複顯示為兩筆待辦。故障恢復或官方完成後，解決原上傳問題並更新原操作，不另造新申請。

### 2.2 折讓開立：主管一次核准，程式連續完成

1. 員工沿原發票提出折讓，保留原因、含稅／未稅與品項、數量、負數折扣、七位固定小數、合法多次部分折讓及超額檢查。
2. 主管直接開啟該筆詳情：同畫面顯示原發票完整資訊、既有折讓、最新可折餘額、本次品項／金額、原因與申請人。不要求抄 ID、另開官方預覽或先按接手。
3. 主管確認並驗證當次權限後，按一次「核准並開立」。
4. 原業務 owner 連續完成最新官方狀態／餘額檢查、核准內容保存、配號、送出及查回。配號與狀態轉移是內部步驟，不另要求主管預留、重登入或點第二個送出按鈕。
5. 同一次操作維持畫面與選取，完成後自動更新清單。若最新資料使原核准內容失效，說明實際差異並讓主管重新確認；不得默默更改核准金額。
6. 官方受理但尚未上傳完成時放「處理中」自動追蹤；能可靠對應該申請的官方完成結果可完成業務，不再以缺少額外的本次 POST 歸因證明而永久維持 sending。外部既有同號仍不得直接冒認本次新折讓。
7. 原申請 ID、防連點／跨機並行修改、核准內容與每次 API 嘗試紀錄保留。同一次已成功或結果不明的 g0401 不因刷新、重開、換裝置而盲目再開一張；完成後不能把歷史送出鎖當成同原發票後續合法部分折讓的永久佔用鎖。

**佔號自動加號（使用者明確決定）：**收到光貿有效回覆 `4040161`／`4040162` 的明確佔號拒絕，就自動加一號再送，**不設換號次數上限**，不另要求主管覆核、文字確認、不同買方證明或人工預留。每次號碼／回覆與進度均記錄，畫面可見且可取消；中斷後先按原申請查明最後一次結果再接續，不能從第一號重跑。逾時／斷線、結果不明或其他錯誤不當成佔號，先查原號。無效／超出既有合法編號格式屬編號錯誤，不藉格式限制偷設換號次數上限。此為使用者指定的佔號處理，與故障自動重試分開，不套用人工設定的碰撞重試上限。

### 2.3 折讓作廢：完整資料、一次核准、立即執行

1. 員工指定原折讓及原因提出作廢。
2. 主管開啟原待辦，同畫面看到原發票完整資訊、原折讓完整資訊、作廢原因與申請人，確認後按一次「核准作廢」。
3. 程式即時確認主管權限、公司／環境及官方狀態，保存核准與操作紀錄，直接執行原號 g0501 並更新結果。
4. 移除「核准後保留15分鐘」、再次輸入「作廢 原號」、另按單次送出及跨 Local／Cloud 永久唯一送出交接門檻。保留一般權限、防連點、必要資料一致性與紀錄；原核准僅約束同一凍結內容；背景恢復仍須確認原主管有效權限、Device／公司與當前交易狀態。
5. 原號已作廢時直接同步完成，紀錄可區分本次操作與先前已作廢，不要求證明一定由本次 POST 造成才結案；`4050132` 轉官方查證，`4050141` 等待官方處理。
6. 逾時先查同一原號；必要時允許同號有限次重試，而非永久禁止第二次 g0501。每次重試核對原操作、當前權限與官方狀態，不因重試建立新的作廢申請。次數／退避參數於實作前在同一計畫明列，不擴散成新平台。
7. 官方處理中列既有「處理中」並自動追蹤；仍無法確認、明確拒絕或本機保存異常才列「上傳問題」並附診斷。

光貿依據：[API 文件](https://invoice.amego.tw/api_doc/)、[API 錯誤代碼](https://invoice.amego.tw/info_detail?mid=71)。本計畫未宣稱供應商保證任意並行 g0501 都冪等；程式須辨識回覆與原號官方狀態。
