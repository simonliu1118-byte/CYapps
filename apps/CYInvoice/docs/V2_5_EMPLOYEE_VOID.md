# CYInvoice V2.5 員工帳戶與發票作廢設計

本文件記錄 CYInvoice V2.5 已確認的產品設計與分批實作狀態。它是設計／需求文件，不是新的永久治理規則；永久規則仍以根目錄 `REPOSITORY_RULES.md`、`REPO_POLICY.md` 與 `apps/CYInvoice/PROJECT_RULES.md` 為準。

最新正式 Release 仍為 V2.4.2；V2.5.0 Build 0 為工程開發基準。V2.5 先完成可完全不依賴雲端帳戶服務運作的本機員工帳戶與正式發票作廢流程；雲端同步、Email 密碼重設等功能留待後續版本。

## 1. V2.5 範圍

V2.5 納入：

- 本機員工清單與帳戶管理。
- 員工密碼驗證與三級權限。
- 唯一超級管理員與離線災難恢復碼。
- 正式發票作廢核心。
- 作廢原因與操作員工編號送入 AMEGO `CancelReason`。
- 作廢前發票號碼人工 double check、員工身分驗證及責任提示。
- 紙本電子發票證明聯狀態覆核，以及「尚未收回」的主管人工確認特殊流程。
- 作廢送出後以 AMEGO 官方查詢確認最終結果。
- 作廢狀態與既有同步、清單、詳細資訊及必要 Cache 行為整合。

V2.5 不納入：

- Cloudflare Workers / D1。
- 雲端 API 位址與裝置授權。
- A/B 機員工帳戶同步。
- Email 驗證碼／忘記密碼寄信。
- MO 密碼雲端同步。
- 多台電腦共用登入失敗計數。
- AMEGO App Key 雲端化或現行儲存機制重構。

V2.5 完成時，即使完全沒有任何雲端帳戶服務，也必須能正常使用員工帳戶與員工作廢功能。實際呼叫 AMEGO 開立、查詢或作廢仍需要能連線到 AMEGO。

## 2. 單一本機員工資料模型

不建立「單機帳戶系統」與「雲端帳戶系統」兩套邏輯。

V2.5 的本機員工資料就是正式資料來源；未來接上雲端後，同一份本機資料改作同步後的離線 Cache。CYInvoice 的員工驗證與作廢流程仍讀同一個本機介面，不因有無雲端而重寫。

```text
V2.5
本機 employees -> CYInvoice

後續版本
Cloud -> 同步 -> 本機 employees -> CYInvoice
```

因此未來即使雲端暫時不可用，已同步到本機且仍有效的員工資料仍可支援必要的本機操作；具體同步衝突與離線有效期限等規則留待雲端版本設計。

## 3. 員工資料

每位員工至少包含：

- 員工編號：固定 4 碼數字，唯一。
- 姓名：必填。
- Email：V2.5 先保存，後續供 Email 密碼重設使用。
- 密碼安全雜湊：不得保存明文或可逆密碼。
- 權限角色：`SUPER_ADMIN` / `ADMIN` / `EMPLOYEE`。
- 啟用狀態。
- 建立／最後修改時間：保留供後續同步使用。

員工資料存於既有 `Data/CYInvoice.db`，以獨立 `employee_schema_version` 管理員工 schema，不改寫既有發票 `schema_version=1` 的語意。

## 4. 三級權限

### 4.1 SUPER_ADMIN

每套本機員工資料只允許一位超級管理員。

超級管理員：

- 具有帳戶管理最高權限。
- 不可降級為 `ADMIN` 或 `EMPLOYEE`。
- 不可取消超級管理員權限。
- 不可停用。
- 不可刪除。
- 一般管理員不得直接重設其密碼。
- 上述限制必須在業務／資料層強制執行，不能只靠 UI 隱藏或 disabled 按鈕。

### 4.2 ADMIN

管理員可以：

- 進入帳戶管理。
- 新增員工。
- 修改一般員工／其他管理員基本資料。
- 重設一般員工／其他管理員密碼。
- 啟用／停用一般員工。
- 將一般員工提升為管理員。
- 取消其他一般管理員的管理員權限。
- 處理「尚未收回紙本電子發票證明聯」所產生的作廢人工確認。

管理員之間可以互相取消對方權限，但管理員不得自行取消自己的管理員權限；若要降級目前登入的管理員，必須由另一位管理員或超級管理員操作。

一般管理員不得對唯一超級管理員執行降級、停用、刪除或直接密碼重設。

### 4.3 EMPLOYEE

一般員工可以正常使用 CYInvoice 與使用自己的員工編號／密碼進行作廢身分驗證，但不能進入帳戶管理，也不能批准或取消主管人工確認。

## 5. 超級管理員離線災難恢復

單機模式不能依賴 Email 或雲端救援，因此 V2.5 使用獨立的「超級管理員復原碼」。

### 5.1 建立

建立第一位超級管理員後，CYInvoice 自動產生一組高強度、適合人工抄錄的復原碼，格式為：

```text
CYR-XXXX-XXXX-XXXX-XXXX-XXXX
```

- 復原碼只在產生當下顯示完整內容。
- CYInvoice 本機只能保存復原碼的安全 Hash，不得保存可讀回的原始碼。
- 畫面需明確提醒超級管理員將復原碼保存於安全的公司文件／離線位置。

### 5.2 使用

超級管理員忘記密碼時，可使用「員工編號 + 復原碼 + 新密碼」重設自己的密碼。

必須確認：

- 目標帳號確實為唯一 `SUPER_ADMIN`。
- 復原碼驗證成功。
- 新密碼符合密碼規則。

一般管理員即使知道自己帳號密碼，也沒有直接重設超級管理員密碼的權限；只有實際持有復原碼者可走此恢復流程。

### 5.3 一次性與輪替

- 復原碼成功使用一次後立即失效。
- 系統產生新的復原碼並只顯示一次，要求重新保存。
- 超級管理員登入帳戶管理後可主動重新產生復原碼；新碼產生後舊碼立即失效。
- 密碼與復原碼同時遺失時，V2.5 不提供一般管理員後門繞過超級管理員保護。

Email 密碼重設功能日後上線後，Email 可成為額外復原途徑；離線復原碼仍保留作為雲端／Email 不可用時的最後救援方式。

## 6. 舊管理密碼遷移

V2.5 員工權限系統完成後，現行獨立「CYInvoice 管理密碼」退出日常管理機制。

舊版資料升級第一次進入 V2.5 時：

1. 驗證目前既有 CYInvoice 管理密碼。
2. 建立第一位員工：4 碼員工編號、姓名、Email、新員工密碼。
3. 此第一位員工自動成為唯一 `SUPER_ADMIN`。
4. 產生並顯示一次超級管理員復原碼。
5. 清除舊管理密碼 salt/hash，日常管理改用員工編號、員工密碼及角色權限。

若第一位超管已成功建立，但清除舊管理密碼時中斷，後續啟動仍應再次完成清除。

全新安裝沒有舊管理密碼可遷移時，第一次設定直接建立第一位超級管理員並產生復原碼。

## 7. 帳戶管理 UI

主畫面有獨立「帳戶管理」入口，與一般「設定」分開。

進入帳戶管理時要求：

```text
員工編號
員工密碼
```

只有啟用中的 `ADMIN` / `SUPER_ADMIN` 可進入。

帳戶清單至少顯示：員工編號、姓名、Email、權限、啟用／停用狀態。

操作包含新增、修改、重設密碼、啟用／停用、設為管理員、取消管理員權限，以及超級管理員復原碼重新產生入口。

超級管理員的不可變限制仍由底層強制，不以 UI 是否顯示按鈕作為唯一保護。

## 8. 作廢入口與前置查詢

作廢按鈕只存在發票詳細資料，不直接放在已開立發票清單。

流程：

1. 使用者從清單雙擊發票。
2. 每一張發票都先執行 `invoice_query`，不得因本機 Cache 看似最新而跳過。
3. 只有 fresh query 後仍為已開立、沒有 `wait.C0501`、官方 upload status 99，且公司／環境一致的發票才可進入作廢流程。
4. 已作廢、`已開立（等待作廢）`、資料不符、query 失敗、環境／公司不符或其他狀態不確定時不得再次送出作廢。

V2.5 不額外加入本機跨期規則；可否作廢以 AMEGO API 的正式結果為準。

## 9. 作廢原因與 CancelReason

作廢第一步由使用者輸入原因，最多 15 字。

AMEGO 官方 `CancelReason` 上限已確認為 20 字。CYInvoice 固定送出：

```text
<4碼員工編號> <使用者輸入原因>
```

例如：

```text
3015 退貨
```

4 碼員工編號 + 1 個空格 + 最多 15 字原因，總長不超過 20 字。

若作廢先進入主管人工確認，最後批准送出時仍保留**原申請員工編號**，不改成批准主管的員工編號。主管的角色是批准該次申請，不取代原始操作人。

## 10. 發票作廢確認視窗

作廢原因輸入完成後，進入獨立「發票作廢確認」視窗。

一般發票確認欄位：

```text
發票號碼  [                    ]
員工編號  [        ]
員工密碼  [                    ]
```

紙本發票另外增加：

```text
證明聯狀態  [未列印／未交付 | 已收回 | 尚未收回]
```

若選「尚未收回」，同一列立即提示：

> 未收回作廢需由管理員確認後才會送出

載具等非紙本發票不顯示證明聯狀態。

### 10.1 發票號碼 double check

此欄位的目的不是讓員工照畫面抄寫，而是要求操作員拿 ERP 紀錄、紙本發票或其他正式來源重新核對。

因此確認視窗：

- 不顯示目前正確發票號碼。
- 不顯示可直接照抄的完整發票資訊。
- 發票號碼輸入欄不得預填。
- 程式只在背景將輸入值與目前準備作廢的發票號碼比對。
- 不符時只提示「發票號碼不符，請重新確認」，不得回顯正確答案。

### 10.2 員工驗證

送出作廢或建立人工確認前必須確認：

- 員工編號合法且存在。
- 員工目前為啟用狀態。
- 密碼驗證成功。

任何驗證失敗都不得呼叫 AMEGO 作廢 API。

帳號不存在、編號格式不合法、停用或密碼錯誤，對外錯誤訊息統一為「員工編號或密碼錯誤」，避免洩漏帳號是否存在。

## 11. 責任聲明與紙本證明聯覆核

V2.5 第四批已重新確認責任聲明與互動形式。

正式責任提示為：

> 本人已核對本次作廢之發票號碼、交易事實、作廢原因及紙本電子發票證明聯收回狀況。
>
> 本人了解發票作廢應依相關法令及公司作業規範辦理；如因本人故意、操作錯誤或疏失致生相關問題，願依實際責任歸屬、相關法令及公司規定負應負之責任。
>
> 按下「確認作廢」即表示本人已閱讀並確認上述事項。

不另外設「同意責任聲明」Checkbox；按下「確認作廢」本身即代表已閱讀並確認。

### 11.1 紙本證明聯三種狀態

紙本發票必須選擇：

1. `未列印／未交付`：可走正常作廢流程。
2. `已收回`：可走正常作廢流程。
3. `尚未收回`：**不立即呼叫 AMEGO，也不呈現為作廢失敗**，改進入「人工確認」。

此特殊流程只適用紙本電子發票證明聯；非紙本發票不顯示此選項。

### 11.2 「尚未收回」人工確認流程

```text
一般員工提出作廢
→ 發票號碼 + 員工帳密驗證成功
→ 證明聯狀態 = 尚未收回
→ AMEGO 呼叫數 = 0
→ 發票本身仍維持「已開立」
→ 上傳問題新增「人工確認」
```

人工確認暫存必要資訊：

- 原申請員工編號。
- 作廢原因。
- 提出時間。
- 發票／訂單識別由既有發票紀錄與 issue 資料提供。

不得保存員工密碼。此資料只為跨程式重啟接續人工確認，處理完成後移除，不建立永久作廢 audit。

### 11.3 主管處理

只有啟用中的 `ADMIN` / `SUPER_ADMIN` 可以處理人工確認。

人工確認提供兩個動作：

- `確認送出作廢`
- `取消退回`

主管操作時必須驗證管理員帳密；底層服務也必須再次驗證角色與帳密，不能只依賴 UI 已登入。

`確認送出作廢`：

1. 重新查詢 AMEGO 最新狀態。
2. 重新套用既有作廢防重／pending 安全語意。
3. 確認仍可作廢後才呼叫 `f0501`。
4. `CancelReason` 使用原申請員工編號與原原因。
5. 若已確認成功或已進入遠端等待作廢，人工確認工作結束；後續由正式作廢狀態流程接手。

`取消退回`：

- 不呼叫 AMEGO。
- 清除本機人工確認資料。
- 發票維持「已開立」。
- 若作廢已經送出或已有核心 pending marker，禁止再取消退回。

人工確認必須依目前公司統編與 test/prod 環境隔離。

## 12. 密碼錯誤節流

V2.5 不做長時間永久鎖帳，作廢驗證採本機記憶體內漸進式節流：

- 第 1～2 次：正常重試。
- 第 3 次：約 5 秒。
- 第 4 次：約 15 秒。
- 第 5 次以上：約 60 秒。
- 驗證成功後清除相應失敗狀態。

節流不得把密碼、Hash、復原碼寫入 log。後續雲端版本再決定如何將多台電腦的失敗計數中央化。

## 13. AMEGO 作廢結果安全語意

正式作廢 API 為 `/json/f0501`。不能僅因 `f0501` 回傳 `code=0` 就立即把本機狀態當成最終成功。

送出前：

- fresh `invoice_query` / `invoice_status` 檢查。
- 已作廢不重送。
- 已有 `C0501` 待處理不重送。
- 官方狀態不是 99 不送。
- 在真正呼叫 `f0501` 前先持久化本機 pending marker，避免 crash／restart 後盲目重送。

送出後：

- 官方明確確認作廢成功 → `已作廢`。
- 官方明確失敗 → 作廢未完成／可依狀態重新處理。
- timeout、傳輸結果不明或 `invoice_query.wait` 已有 `C0501` → `已開立（等待作廢）`，保留 pending marker 並禁止盲目重送。

`invoice_status=99` 表示原發票上傳完成；即使發票正處於 `已開立（等待作廢）`，99 仍維持「完成」及既有綠燈語意，不因作廢流程改成另一種顏色或狀態。

結果不明時禁止盲目重送 `f0501`。pending 紀錄再次操作時先 reconciliation；若官方明確仍為正常已開立且沒有待處理作廢，只解除 pending 並要求重新確認，同一次操作不自動重送。

## 14. 作廢資料、同步與 AMEGO 權威

AMEGO 官方資料仍是發票狀態的權威來源。

已確認 API 資料語意：

- `invoice_list` 提供 `cancel_date` 與 `invoice_status`，不提供 `wait[]`；正常啟動／5 分鐘／手動同步以既有 list 流程為主。
- `invoice_query` 提供 `cancel_date`，並可由 `wait[]` 中的 `C0501` 辨識等待作廢。
- CYInvoice 自己送出作廢後，本機 pending marker 立即維持 `已開立（等待作廢）` 並防止重送；後續 list 一旦取得 `cancel_date > 0` 即收斂為 `已作廢`。
- 只有 pending 發票已超出近 3 天 list 覆蓋範圍時，才使用核准的例外流程：針對該張發票單筆 query 作補充確認，不自動重送 `f0501`。
- list、同步 query、詳細資料 query 共用同一套官方狀態映射，避免不同入口對相同資料做不同解讀。
- 作廢正式確認後清除 pending marker，並使舊 PDF／preview Cache 失效。

第五批仍需用測試環境送出例如 `3015 退貨`，檢查完整原始 `invoice_query` JSON 是否實際回傳未文件化的作廢原因欄位：

- 若官方 query 可取回原因，正常同步／顯示。
- 若官方 query 不提供原因，不為補足此欄位另外建立永久本機 `void_audit`。

V2.5 也不建立龐大的永久本機 auth audit。

## 15. App Key 與 MO 密碼

### 15.1 AMEGO App Key

V2.5 完全維持現行 App Key 設計，不修改：

- 各電腦由管理者自行設定。
- 使用目前 Windows DPAPI 保護。
- 不上雲。
- 不同步。
- 不為員工系統或復原碼重構 App Key 儲存方式。

App Key 不得拿來當作超級管理員密碼復原憑證。

### 15.2 MO 密碼

V2.5 維持目前本機儲存／使用方式；未來雲端同步另案處理。

## 16. 後續雲端方向（不屬於 V2.5）

後續版本再加入可選 API 位址、免費雲端服務、員工同步、Email 重設、Device Token、MO 密碼同步等能力。

未來 API 位址可由使用者設定；沒有設定時仍可完全以本機員工資料運作。同一套 CYInvoice EXE 因此可以支援總公司雲端同步、分公司獨立單機以及其他公司各自設定自己的 AMEGO App Key。

雲端上線後仍沿用 V2.5 的本機員工資料模型作離線 Cache，不另外建立第二套員工權限流程。
