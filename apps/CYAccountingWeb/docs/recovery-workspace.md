# 按需建立還原工作區

一般發布預設使用 `disabled`：不建立、查找、遷移或綁定還原資料庫。既有資料庫會保留，清理另行確認。自動備份、08:00 補跑及記憶體內的還原驗證維持原流程。

## 需要還原時

1. 維運先確認帳號仍有一個資料庫名額，並核對本次備份與還原範圍。
2. 在現有 **CYAccountingWeb Validate and Deploy** 的 Run workflow 選擇 `main`，將 `recovery_workspace` 選為 `prepare`。只能使用已審核的當前 main；沿用既有受保護部署入口，不從網頁建立雲端資源。
3. 此模式建立一個獨立空白工作區，或重用唯一且通過初始資料核對的工作區。正式帳本不執行 migration，避免原資料庫無法使用時阻擋復原準備。工作區本身套用正式 migration。
4. 確認相同 source SHA 的 deploy job 成功後，再使用既有還原視窗或緊急復原入口，預覽備份、輸入理由與確認文字、還原並核對。
5. 完成核對後，正式切換、解除綁定及清理分別由維運處理；保留原帳本及稽核，不自動升格或刪庫。

正在進行復原時應暫停一般發布；一般 `disabled` 發布會解除還原綁定，資料庫內容仍保留。已含還原資料的工作區不接受再次 `prepare`；需要重新綁定或切換時，先核對原工作區與既有完成證據。

## 失敗與名額不足

- 沒有可用名額、權限不足或超額時停止，不刪其他資料庫、不迴圈重試。
- 找到多個可能工作區時停止，不自動選最新的資料庫。
- 既有工作區不符合空白初始狀態時，停止於 migration 與寫入之前。
- 工作區尚未建立時，介面顯示準備提示；緊急入口不因此讀取正式帳本或列出備份。

## 後續清理階段

本階段只改程式與部署選項，不刪雲端資源。發布後，由可用的 Cloudflare MCP 核對待清理庫：目前所有 Worker／版本的綁定、資料庫用途及還原／稽核狀態。不能以名稱、建立日期、容量或畫面零讀寫推定可刪。

確認未被使用、所需資料及證據已保留後，再處理資源清理。若資料庫已成為正式帳本，或含尚待處理的還原結果，停止清理。不要清空正式庫來騰名額。

## 本次範圍與驗收

- `src/backup-service.js` 與既有還原引擎維持唯一業務入口；沒有第二套還原 writer、額外網站權杖或新 workflow。
- 一般發布預估還原資源 API 呼叫 0、還原庫讀寫 0。
- `prepare` 最多兩頁清單、一次建立、六次有界 metadata／初始狀態查詢，另加 canonical migration。初始狀態快速檢查只讀各表至多初始列數加一；不查正式帳務。
- 本地及 CI 使用合成資料測試預設零呼叫、明確啟動、重用、拒絕已使用庫、清單上限、權限／名額／額度失敗與原帳本隔離。
- 正式 Cloudflare 綁定、按需建立及名額釋放另待發布後驗收，不以測試結果冒充已刪除資源。
