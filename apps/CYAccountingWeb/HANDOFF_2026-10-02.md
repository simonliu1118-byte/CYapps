## Completed behavior

- `src/opening-balances.js` is the only current opening calculation/API owner. Old core GET/PUT ownership is removed. Current D1 runtime has no dependency on `opening_balances`; the desktop SQLite source reader still reads that desktop-schema table.
- Without an override, opening is all prior income minus expense. A prior override supplies a new baseline, then transactions from that baseline month onward carry forward. Exact-month override replaces that month's opening.
- Manual override requires a reason, checks the month lock, writes override and audit atomically, and gets actor only from the resolved CYID principal. Audit stores the actual effective old/new amount, not just a previous override or client actor.
- Returning to automatic amount deletes that month's override and appends a `clear` audit. Manual UI waits for server success and shows old → new values in audit. Normal view is read-only calculation; manual action enters edit mode.
- `USER` cannot write; `ADMIN` / `SUPER_ADMIN` can adjust unlocked months. Identity remains CYID; no new auth/session authority.
- Excel export calls the same snapshot and labels automatic/manual values.
- Migration 0006 copies every old row into overrides and migration audit, then drops the old table and records schema 6. Database triggers reject audit UPDATE/DELETE.
- Backup inner format v2 adds account archive state, opening overrides and audit. Outer `CYAccountingWebBackupSet / formatVersion 2` stays stable; manifest describes inner format and actual source app version. Legacy v2 objects remain readable without rewriting.
- Desktop opening import produces override + migration audit using the resolved session actor. Opening JSON chunks use 2,000 rows; worst supported migration stays at 40 statements, below D1 invocation/bind/payload budgets covered by tests.

## Permanent account deletion semantics

SUPER_ADMIN can permanently delete an archived account only when it has zero transactions and its latest effective opening baseline is zero. With no transactions, latest override equals effective opening; an earlier non-zero override alone no longer blocks.

- Same-month non-zero override later cleared to automatic zero: deletable; audit stays.
- Earlier non-zero override followed by newer zero: deletable; retain both baseline rows and all audit, keeping historical balances unchanged.
- Only zero overrides: they may be cleaned up while deleting the master account; audit stays.
- Any transaction, non-zero latest baseline, unarchived account or non-SUPER_ADMIN role: blocked.
- Audited account names cannot be reused through create/rename, preventing historical financial rows from leaking into a new master account.

Do not cascade-delete transactions, historical non-zero values or audit, and do not recreate wrapper/version owners.
