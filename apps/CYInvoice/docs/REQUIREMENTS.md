# CYInvoice 功能基準

本文件描述目前 C#／WinForms 產品行為；永久治理規則仍以 `PROJECT_RULES.md` 為準。

目前開發／工程測試基準為 **V2.4.0**；最新公開正式 Release 仍為 **V2.3.0**。V2.4.0 未經使用者明確要求不得建立正式 Release。

## 平台與基本開立

- Windows 10/11 x64 可攜式 GUI EXE，C#／.NET 10／WinForms，自 V2.0.0 起為唯一正式產品線。
- 支援手動開立、MO店+、酷澎及鼎新 ERP 匯入開立。
- 訂單編號可自動產生或自訂；手動自動編號格式為 `MYYYYMMDDXXX`。
- 一般消費者只能使用含稅模式；公司統編可切換含稅／未稅。固定精度運算不得以二進位浮點累積誤差取代；驗收基準包含 `200 → 190.4761905 → 200`。
- 商品明細最多 50 筆；完全空白列可在最後開立時忽略，部分填寫列必須提示補齊。品名／數量／單價 Enter 流程：品名 → 數量 → 單價；單價 Enter 後若已有下一筆就移到下一列品名，否則新增一列並移到新品名。
- 發票總備註最多 200 字。

## 防重複與開票安全

- 防重複鍵為「來源＋原始平台訂單編號＋環境」。同來源同原始訂單已有已開立、結果不明、資料變更中或其他未明確可重開狀態時禁止再次開立。
- 明確失敗或已作廢才允許重開；作廢後重開的 API OrderId 依序使用 `-R2`、`-R3` 等可追蹤尾碼，本機仍保存原始平台訂單編號。
- 同一時間只允許一個 CYInvoice 程序；同一程序的開立流程序列化「防重檢查 → 建立待處理紀錄 → 送出」。
- AMEGO 已成功開立與本機保存成功是兩種不同狀態。遠端已開立但本機保存失敗時不得當作一般失敗重送。
- 網路逾時或傳輸結果不明時，以獨立限時唯讀查詢回查；無法嚴格確認則標記「結果不明」並禁止自動重送。
- 開票後安全回查不能只比 OrderId；必須唯一命中並核對必要欄位，包括發票號碼、銷售額、稅額、總額、DetailVat 與作廢狀態。
- 上傳狀態只有 AMEGO 明確回覆 `99` 才是完成；`91` 為錯誤；其他處理中／未知狀態不得視為成功。
- V2.4.0 的同步只做官方查詢與本機 Cache 更新，不得因同步呼叫開立 API 重送發票，也不得放寬上述安全規則。

## 公司統編與買方名稱

- 手動開票與鼎新匯入共用同一套公司統編／買方名稱查詢行為。
- 輸入完整 8 碼統編後自動查詢：先查本機人工名稱記憶，再查光貿 API。
- API 技術失敗不得冒充「查無名稱」；光貿正常回覆但名稱空白時才允許人工輸入。
- 光貿查得到的公司名稱不存成人工名稱記憶；只有 API 正常但名稱空白、使用者人工輸入且發票最後確認成功時才保存到 SQLite `buyer_names`。
- 若人工買方名稱與最近一次 API 名稱不同，以紅字提示並在欄位右側顯示 `↻`；`↻` 直接重查 API、繞過本機名稱。按鈕不得改變 TextBox 原本外框、高度或版面，滑鼠游標使用可點擊手形。
- 任何舊的非同步查詢結果都不得覆蓋使用者後來輸入的新統編／名稱。

## 測試環境去識別化

- 光貿測試環境是跨公司共用測試池，本機畫面與本機紀錄仍可保存原始資料，但送往測試 API 的可識別資料必須去識別化。
- 一般消費者測試開票使用既有測試消費者資料。
- 公司戶測試開票不得送出真實買方統編／名稱；固定改用公開測試統編 `28080623`，並於送出前向光貿 API 查詢該測試統編的正式名稱。若測試統編查不到名稱，停止送出，不使用假名稱硬送。
- 地址、電話、Email、捐贈碼、主備註、明細備註與商品文字等可識別資料依測試隱私規則清空或替換；正式環境不得套用這些替換。
- V2.4.0 的測試環境同步不得使用 `invoice_list` 掃描共享測試池；只回查本機當日已知測試紀錄。

## Excel 匯入

### 共用確認流程

- MO店+、酷澎、鼎新 ERP 的解析器只負責把來源 Excel 轉成共用訂單資料；選檔後都進入同一套「開立發票匯入確認」流程。
- 確認視窗顯示解析、統編查詢、檢查狀態與開立進度；取消、未勾選、資料有問題或結果不明的訂單不得送出。
- 匯入確認的檢查狀態使用直接操作語意，例如「可開立」、「已有開立紀錄，禁止重送」、「開立結果待確認，禁止重送」。

### MO店+

- 原始 `OrderExport` 依完整欄名辨識，不依檔名或固定欄位位置；受密碼保護的 `.xls` 由 Excel COM 唯讀開啟，停用巨集、外部連結更新、事件及提示，不建立中介 Excel。
- 官方「開立發票金額_依品項」及官方加總欄位是消費者發票金額最高準則；不得以商品售價、平台淨入帳或自行折扣邏輯覆蓋。
- 有買方統編的 MO 訂單為公司紙本；沒有統編的訂單使用既有會員載具流程。
- 公司 MO 含稅總額依既有 DetailVat=1 拆分為未稅銷售額與稅額，總額不得因拆稅而改變。

### 酷澎

- 支援已寄出 DeliveryList `.xlsx`，依欄名與必要欄位辨識，不依檔名或固定欄位位置。
- 「應開立予買家之發票金額」作為買家發票依據；「應開立予酷澎之發票金額」不得計入買家發票。
- 尚未取得可靠樣本的未出貨、公司統編、特殊折扣或無法安全推導的格式必須保守停止，不猜測欄位或金額。

### 鼎新 ERP

- V2.3.0 起正式支援鼎新 ERP `.xlsx` 直接匯入；一個活頁簿必須只代表一張銷貨單。
- 必須找到「單頭資料」與「單身資料」。單頭必要欄位：`銷貨單號`、`客戶全名`、`統一編號`、`本幣合計`。
- 單身必要欄位：`品名`、`數量`、`金額`；`單位` 為選填，存在時保存並傳送至 AMEGO `ProductItem.Unit`。
- 單身 `金額` 是權威值；單價由 `金額 ÷ 數量` 推導，不使用鼎新原始單價覆蓋金額。數量必須大於 0；金額可為正、零或合法負數折扣。
- 所有單身 `金額` 加總必須等於單頭 `本幣合計`，且整張總額必須大於 0；不做金額重新分攤。
- 原始統編／客戶名稱保留供確認視窗核對。公司戶可修改統編／名稱，修改後必須按「套用資料」才可開立；兩欄必須同時有值或同時空白。
- 鼎新一律紙本。若統編空白則依一般消費者處理，不顯示無意義的原始公司名稱。

## V2.4.0 本機資料與權威來源

- 主要本機資料庫為 `Data/CYInvoice.db`；`Data/settings.json` 繼續獨立保存安全設定。
- SQLite 保存發票、商品明細、人工買方名稱、同步狀態及同步問題；詳細欄位與遷移規則見 `DATA_FORMAT.md`。
- 第一次啟動且 DB 不存在時，舊 `invoices.json`／`buyer_names.json` 必須先完整讀取，在暫存 SQLite transaction 中匯入並驗證後才原子切換；舊 JSON 保留，不自動刪除。
- 損壞舊 JSON、損壞既有 DB 或 schema 驗證失敗時停止並回報，不得以空資料庫覆蓋。
- SQLite 使用技術 `local_id` 主鍵；發票號碼／OrderID 不設過度嚴格 business UNIQUE。同步若找到多筆本機候選，停止自動猜測，不任意覆寫。
- AMEGO／光貿官方資料是發票內容權威來源；SQLite 是本機 Cache 加上 CYInvoice 本機 metadata。遠端買受人、統編、金額、商品、作廢／重開與上傳狀態變更屬正常更新，不因內容不同建立衝突。

## V2.4.0 發票同步

- 正式環境 recent sync 以 `/json/invoice_list` 為主要來源，範圍為今天與前 2 天，共最近 3 天。
- 程式啟動、開啟期間每 5 分鐘及手動「重新整理狀態」共用同一套 recent sync 核心；同時間只執行一個同步，重疊要求直接略過、不排隊。
- 手動同步完成後有 30 秒冷卻，避免連續重查。
- 每個本機日第一次自動同步，正式環境改做目前兩月發票期別加上一期的較廣校對；同日後續自動同步回到 recent 3 天。
- recent/daily sync 只在需要時執行 `invoice_query`；同步不得直接重送發票。
- `invoice_list` 清單或 query 回傳的官方發票內容可更新本機 Cache；本機來源／record origin 等 CYInvoice metadata 依用途保留。
- 同一發票號碼或 OrderID 對到多筆本機候選時，記錄 `ambiguous_match`，停止該筆自動更新，不自行挑一筆。

## 已開立發票清單、詳細資訊與同步問題

- 清單預設日期為本月第一日至今天，可依發票號碼、訂單編號、買受人、統編、來源及發票狀態篩選；來源包含鼎新 ERP 及光貿同步來源。
- 單擊發票號碼可直接複製；空白斑馬列不可選取或雙擊。
- 雙擊任何實際發票，不論日期是否超過 recent 3 天，都必須先執行 `invoice_query` 更新該張 SQLite Cache，再以最新本機內容開啟詳細資訊。
- 若雙擊時無法向光貿確認最新資料，不開啟舊詳細資訊冒充最新內容；本機 Cache 保留不變並提示無法確認。
- 「同步問題」視窗只顯示目前帳號的未解決技術問題，可標記完成、刪除或重新整理。刪除問題紀錄不得刪除發票。
- 真正的技術問題包括 invoice list／query 失敗、光貿查無、結果不明仍無法確認、本機 DB 寫入失敗、解析／比對失敗及 ambiguous match。
- 買受人、金額、商品、統編或官方狀態變動不是同步問題。
- 相同未解決問題按帳號＋發票／OrderID＋問題類型去重；後續成功同步可自動標記解決。

## 本機資料保留

- 正式環境只保留目前及上一個兩月發票期別的本機發票／明細 Cache。
- 測試環境只保留當日資料。
- 清理在成功的較廣同步後執行；能確認日期已超出保存範圍的舊資料會刪除，即使舊狀態是 `Unknown`／`Changing` 亦不永久保留。
- 與被刪發票直接對應的舊 sync issue、PDF Cache 與 preview Cache 一併清理。
- 無法判定日期的紀錄不得靠猜測刪除。

## 紙本 PDF、詳細資訊與列印

- 同環境、已開立、未作廢且有發票號碼的紙本發票可透過 `/json/invoice_file` 取得官方 PDF，不以上傳狀態 `99` 作為取得 PDF 的前置條件。
- 詳細資訊使用官方 A4 style 0 第一頁產生預覽 PNG；完整 PDF 即使有第二頁也不得被預覽裁切流程改寫。
- PDF Cache 依環境、日期、發票號碼與 `download_style` 隔離；第一頁預覽另存 `Cache/InvoicePreview`。損壞 PDF／PNG 不得沿用。
- 一般消費者只使用 A4；公司統編支援 0、1、2、3、5 五種官方版型。版型選擇卡片使用去識別化固定示意圖，選定後才取得真實 PDF。
- 「檢視 PDF」使用 WebView2／Edge PDF Viewer 原生工具列，不增加自製縮放工具列。
- 「列印發票」可直接把官方 PDF 送到 CYInvoice 記住的發票印表機，不開啟可見 PDF Viewer，也不修改 Windows 全域預設印表機。
- 直接列印只列出 Windows 回報支援雙面的印表機。一般消費者固定 A4、雙面、長邊翻轉；公司統編先選官方版型，再使用記住的印表機與其 duplex 設定。
- 會員載具不呼叫紙本 PDF API、不建立 PDF／預覽 Cache、不提供一般紙本列印；詳細資訊使用清楚標示「模擬預覽，非正式憑證」的不可驗證票面與本機交易明細。
- 當官方同步更新該張發票內容時，相關舊 PDF／預覽 Cache 必須失效，避免顯示過時官方資料。

## 安全設定、UI 與發行

- 正式 App Key 與 MO店+ 密碼使用目前 Windows 使用者的 DPAPI；管理密碼使用 salted PBKDF2-HMAC-SHA256（210,000 次）或既有相容格式，不保存明文。
- 全新 Data 或安全設定不完整時，首次設定不可略過；首次環境固定為光貿測試環境。
- 既有 DPAPI 資料若由不同 Windows 使用者／電腦開啟而無法解密，保留原資料並停止，不自動覆蓋。
- 正式客戶資料、發票資料、執行期 DB／LOG、密碼與 App Key 不得進入 Public Git、CI log 或 Release source。
- 主畫面一般狀態使用正式預設尺寸並允許最大化／還原／最小化；主要輸入框不得因附加按鈕而改變原生外框或被裁切。
- 商品與已開立清單維持單一正式欄寬／scrollbar 路徑，不得產生水平 scrollbar 或未命名假欄位。
- 鼎新確認列的統編標題／欄位、買方名稱標題／欄位、套用按鈕與提示文字使用同一條垂直中心線。
- 主視窗底部右側顯示 `Copyright © 2026 C.C. Liu, Chihyuan Co. All Rights Reserved.`。
- 發行 ZIP 根目錄包含 `CYInvoice.exe`、當版唯一 `V版本號.txt` 與 `使用說明.txt`；WebView2 managed DLL 集中在 `Runtime/WebView2`。
- 工程 Artifact 與正式 Release 以 `Channel` 與 Artifact／Release 身分區分；正式 Release 只有在使用者當次明確要求 `release` 後由 `main` workflow 建置。
