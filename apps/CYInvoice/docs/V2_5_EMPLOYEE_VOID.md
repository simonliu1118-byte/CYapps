# CYInvoice V2.5 員工帳戶與發票作廢設計

本文件記錄 V2.5 在開始實作前已確認的產品設計。它是設計／需求文件，不是新的永久治理規則；永久規則仍以根目錄 `REPOSITORY_RULES.md`、`REPO_POLICY.md` 與 `apps/CYInvoice/PROJECT_RULES.md` 為準。

目前正式基準為 V2.4.2 Build 0。V2.5 採分批實作，先完成可完全離線單機運作的員工帳戶與發票作廢流程；雲端同步、Email 密碼重設等功能留待後續版本。

## 1. V2.5 範圍

V2.5 只納入下列主題：

- 本機員工清單與帳戶管理。
- 員工密碼驗證與三級權限。
- 唯一超級管理員與離線災難恢復碼。
- 正式發票作廢流程。
- 作廢原因與操作員工編號送入 AMEGO `CancelReason`。
- 作廢前發票號碼人工 double check、員工身分驗證及責任提示。
- 作廢送出後以 AMEGO 官方查詢確認最終結果。
- 作廢狀態與既有同步、清單、詳細資訊及必要 Cache 行為整合。

V2.5 不納入：

- Cloudflare Workers / D1。
- 雲端 API 位址與裝置授權。
- A/B 機員工帳戶同步。
- Email 驗證碼／忘記密碼寄信。
- MO 密碼雲端同步。
- 多台電腦共用登入失敗計數。
- AMEGO App Key 雲端化或現行儲存機制重構。

V2.5 完成時，即使完全沒有任何雲端服務，也必須能正常使用員工帳戶與員工作廢功能。

## 2. 單一本機員工資料模型

不建立「單機帳戶系統」與「雲端帳戶系統」兩套邏輯。

V2.5 的本機員工資料就是正式資料來源；未來接上雲端後，同一份本機資料改作同步後的離線 Cache。CYInvoice 的員工驗證與作廢流程仍讀同一個本機介面，不因有無雲端而重寫。

概念：

```text
V2.5
本機 employees -> CYInvoice

後續版本
Cloud -> 同步 -> 本機 employees -> CYInvoice
```

因此未來即使雲端暫時斷線，已同步到本機且仍有效的員工資料仍可支援必要的離線操作；具體同步衝突與離線有效期限等規則留待雲端版本設計。

## 3. 員工資料

每位員工至少包含：

- 員工編號：固定 4 碼數字，唯一。
- 姓名：必填。
- Email：V2.5 先保存，後續供 Email 密碼重設使用。
- 密碼安全雜湊：不得保存明文或可逆密碼。
- 權限角色：`SUPER_ADMIN` / `ADMIN` / `EMPLOYEE`。
- 啟用狀態。
- 最後修改時間：保留供後續同步使用。

V2.5 的員工資料存於既有本機 SQLite 架構內；正式 schema 與 migration 需在第一批實作時依目前資料庫設計確認。

## 4. 三級權限

### 4.1 SUPER_ADMIN

每套本機員工資料只允許一位超級管理員。

超級管理員：

- 具有帳戶管理最高權限。
- 不可降級為 `ADMIN` 或 `EMPLOYEE`。
- 不可取消超級管理員權限。
- 不可停用。
- 不可刪除。
- 一般管理員不得直接重設其密碼。
- 上述限制必須在業務／資料層強制執行，不能只靠 UI 隱藏或 disabled 按鈕。

### 4.2 ADMIN

管理員可以：

- 進入帳戶管理。
- 新增員工。
- 修改一般員工／其他管理員的基本資料。
- 重設一般員工／其他管理員密碼。
- 啟用／停用一般員工。
- 將一般員工提升為管理員。
- 取消其他一般管理員的管理員權限。

管理員之間可以互相取消對方權限，但管理員不得自行取消自己的管理員權限；若要降級目前登入的管理員，必須由另一位管理員或超級管理員操作。

一般管理員不得對唯一超級管理員執行降級、停用、刪除或直接密碼重設。

### 4.3 EMPLOYEE

一般員工可以正常使用 CYInvoice 與使用自己的員工編號／密碼進行作廢身分驗證，但不能進入帳戶管理或修改其他員工權限。

## 5. 超級管理員離線災難恢復

單機模式不能依賴 Email 或雲端救援，因此 V2.5 使用獨立的「超級管理員復原碼」。

### 5.1 建立

建立第一位超級管理員後，CYInvoice 自動產生一組高強度、適合人工抄錄的復原碼，例如概念格式：

```text
CYR-7K4M-9Q2X-H8TF-6NPD
```

實際格式與熵在實作時以安全性及可輸入性為準。

- 復原碼只在產生當下顯示完整內容。
- CYInvoice 本機只能保存復原碼的安全 Hash，不得保存可讀回的原始碼。
- 畫面需明確提醒超級管理員將復原碼保存於安全的公司文件／離線位置。

### 5.2 使用

超級管理員忘記密碼時，可使用「員工編號 + 復原碼 + 新密碼」重設自己的密碼。

必須確認：

- 目標帳號確實為唯一 `SUPER_ADMIN`。
- 復原碼驗證成功。
- 新密碼符合當時的密碼規則。

一般管理員即使知道自己帳號密碼，也沒有直接重設超級管理員密碼的權限；只有實際持有復原碼者可走此恢復流程。

### 5.3 一次性與輪替

- 復原碼成功使用一次後立即失效。
- 系統產生新的復原碼並只顯示一次，要求重新保存。
- 超級管理員登入帳戶管理後可主動重新產生復原碼；新碼產生後舊碼立即失效。
- 密碼與復原碼同時遺失時，V2.5 不提供一般管理員後門繞過超級管理員保護。

Email 密碼重設功能日後上線後，Email 可成為額外復原途徑；離線復原碼仍保留作為雲端／Email 不可用時的最後救援方式。

## 6. 舊管理密碼遷移

V2.5 員工權限系統完成後，現行獨立「CYInvoice 管理密碼」退出日常管理機制。

舊版資料升級第一次進入 V2.5 時：

1. 驗證目前既有 CYInvoice 管理密碼。
2. 建立第一位員工：4 碼員工編號、姓名、Email、新員工密碼。
3. 此第一位員工自動成為唯一 `SUPER_ADMIN`，不可選擇其他角色。
4. 產生並顯示一次超級管理員復原碼。
5. 完成遷移後，日常管理改用員工編號、員工密碼及角色權限。

全新安裝沒有舊管理密碼可遷移時，第一次設定直接建立第一位超級管理員並產生復原碼。

## 7. 帳戶管理 UI

主畫面新增獨立的「帳戶管理」入口，與一般「設定」分開。

進入帳戶管理時要求：

```text
員工編號
員工密碼
```

只有啟用中的 `ADMIN` / `SUPER_ADMIN` 可進入。

帳戶清單至少顯示：

- 員工編號。
- 姓名。
- Email。
- 權限。
- 啟用／停用狀態。

操作至少包含：新增、修改、重設密碼、啟用／停用、設為管理員、取消管理員權限，以及超級管理員復原碼重新產生入口。

超級管理員的不可變限制仍由底層強制，不以 UI 是否顯示按鈕作為唯一保護。

## 8. 作廢入口與前置查詢

作廢按鈕只存在發票詳細資料，不直接放在已開立發票清單。

流程：

1. 使用者從清單雙擊發票。
2. 每一張發票都先執行 `invoice_query`，不得因本機 Cache 看似最新而跳過。
3. 只有剛完成的官方查詢確認該發票仍可作廢時，詳細頁才允許進入作廢流程。
4. 已作廢、資料不符、query 失敗、環境／公司不符或其他狀態不確定時不得送出作廢。

V2.5 不額外加入本機跨期規則；可否作廢以 AMEGO API 的正式結果為準。

## 9. 作廢原因

作廢第一步由使用者輸入原因，最多 15 字。

送給 AMEGO 的 `CancelReason` 格式固定為：

```text
<4碼員工編號> <使用者輸入原因>
```

例如：

```text
3015 退貨
```

實作前必須重新確認最新 AMEGO 官方 `f0501` 文件中的 `CancelReason` 長度及格式限制，確保「4 碼員工編號 + 空格 + 15 字原因」符合正式 API 規格。

## 10. 發票作廢確認視窗

作廢原因輸入完成後，進入獨立「發票作廢確認」視窗。

目前已確定此視窗保持精簡，只保留三行輸入：

```text
發票號碼  [                    ]
員工編號  [        ]
員工密碼  [                    ]
```

### 10.1 發票號碼 double check

此欄位的目的不是讓員工照畫面抄寫，而是要求操作員拿 ERP 紀錄、紙本發票或其他正式來源重新核對。

因此確認視窗：

- 不顯示目前正確發票號碼。
- 不顯示可直接照抄的完整發票資訊。
- 發票號碼輸入欄不得預填。
- 程式只在背景將輸入值與目前準備作廢的發票號碼比對。
- 不符時只提示「發票號碼不符，請重新確認」，不得回顯正確答案。

### 10.2 員工驗證

送出 `f0501` 前必須確認：

- 員工編號為合法 4 碼。
- 員工存在。
- 員工目前為啟用狀態。
- 密碼驗證成功。

任何一項失敗都不得呼叫 AMEGO 作廢 API。

帳號不存在或密碼錯誤時，對外錯誤訊息統一為「員工編號或密碼錯誤」，避免洩漏帳號是否存在。

## 11. 責任聲明與證明聯覆核：實作前必須再次確認

「發票作廢確認」視窗需要有清楚的作廢責任提示，但**目前文字與互動形式尚未最終定稿**。

目前只保留以下設計意圖：

- 提醒操作員已確認本次作廢資料。
- 提醒不當或錯誤作廢可能涉及稅務法令與公司內部責任。
- 可考慮以按下「確認作廢」視同已閱讀／了解／同意聲明，避免額外 Checkbox 增加操作負擔。

但是做到此 UI 階段時，必須主動提醒使用者重新仔細確認：

1. 責任聲明的正式文字。
2. 是否仍採「按下確認即視同同意」，或改回明確 Checkbox。
3. 是否需要加入「已收回證明聯／未收回證明聯」等紙本憑證覆核流程。
4. 若加入證明聯選項，各選項是否會影響允許作廢、警告文字或後續處理。

在使用者於該階段再次確認前，不得把目前討論過的責任聲明草稿視為最終文案，也不得自行決定證明聯流程。

## 12. 密碼錯誤節流

V2.5 不做長時間永久鎖帳，先採本機漸進式節流。現階段方向：

- 第 1～2 次：正常重試。
- 第 3 次：約 5 秒。
- 第 4 次：約 15 秒。
- 第 5 次以上：約 60 秒。
- 驗證成功後清除相應失敗狀態。

正式實作時可依 UI 及測試調整細節，但不得因節流造成一般操作員長時間無法工作，也不得把密碼、Hash、復原碼寫入 log。

後續雲端版本再決定如何將多台電腦的失敗計數中央化。

## 13. AMEGO 作廢結果安全語意

正式作廢 API 為 `/json/f0501`。不能僅因 `f0501` 回傳看似成功就立即把本機狀態當成最終成功。

作廢送出後需使用 AMEGO 官方查詢（`invoice_status` / `invoice_query` 等最新適用介面）確認最終狀態。

結果分為：

- 官方明確確認作廢成功 -> 已作廢。
- 官方明確失敗 -> 作廢失敗。
- timeout、傳輸結果不明或官方尚未能確認 -> 作廢結果待確認。

結果不明時禁止盲目重送 `f0501`。後續由既有啟動同步、5 分鐘同步及手動重新整理流程重新確認並自動清除已解決狀態。

## 14. 作廢資料、AMGEO 權威與本機 Audit

AMEGO 官方資料仍是發票狀態的權威來源。

目前公開規格已知 `invoice_query` 有作廢時間相關 `cancel_date`；正式實作前仍需以最新官方文件與測試環境確認實際回傳格式。

V2.5 不為作廢另建永久 `void_audit`，也不建立龐大的本機 auth audit。

實作作廢測試時，應送出例如 `3015 退貨`，再檢查 `invoice_query` 完整原始 JSON，確認 AMEGO 是否實際回傳未文件化的作廢原因欄位：

- 若官方 query 可取回原因，正常同步／顯示。
- 若官方 query 不提供原因，不為補足此欄位另外建立永久本機作廢 audit。

## 15. App Key 與 MO 密碼

### 15.1 AMEGO App Key

V2.5 完全維持現行 App Key 設計，不修改：

- 各電腦由管理者自行設定。
- 使用目前 Windows DPAPI 保護。
- 不上雲。
- 不同步。
- 不為員工系統或復原碼重構 App Key 儲存方式。

App Key 也不得拿來當作超級管理員密碼復原憑證，避免增加高敏感憑證的輸入與暴露場合。

### 15.2 MO 密碼

V2.5 維持目前本機儲存／使用方式；未來雲端同步另案處理。

## 16. 後續雲端方向（不屬於 V2.5）

後續版本再加入可選 API 位址、免費雲端服務、員工同步、Email 重設、Device Token、MO 密碼同步等能力。

未來 API 位址可由使用者設定；沒有設定時仍可完全以本機資料運作。同一套 CYInvoice EXE 因此可以支援總公司雲端同步、分公司獨立單機以及其他公司各自設定自己的 AMEGO App Key。

雲端上線後仍沿用 V2.5 的本機員工資料模型作離線 Cache，不另外建立第二套員工權限流程。

## 17. V2.5 分批實作順序

為降低高風險發票流程一次改動過大的風險，依下列順序分批：

### 第一批：員工核心

- SQLite schema / migration。
- Employee model。
- 4 碼員工編號。
- Password Hash。
- `SUPER_ADMIN` / `ADMIN` / `EMPLOYEE`。
- 啟用／停用。
- 底層角色保護。
- 超級管理員復原碼 Hash、產生、驗證及輪替核心。

### 第二批：帳戶管理

- 主畫面「帳戶管理」。
- 管理員登入驗證。
- 新增／修改員工。
- 一般員工／管理員密碼重設。
- 管理員互相取消權限但不得自我降級。
- 超級管理員不可降級／停用／刪除。
- 超級管理員復原碼首次顯示、忘記密碼復原與主動重新產生。
- 舊管理密碼到第一位超級管理員的遷移。

### 第三批：AMEGO 作廢核心

- 重新核對最新官方 `f0501` / query / status 文件。
- `f0501` request / response。
- `CancelReason`。
- timeout / transport unknown。
- pending / failure / confirmed success。
- 防止盲目重送。
- 作廢後官方狀態確認。

### 第四批：員工作廢整合

- 作廢原因最多 15 字。
- 發票號碼人工 double check。
- 員工編號與密碼驗證。
- 本機登入失敗節流。
- `CancelReason = "員工編號 原因"`。
- 「發票作廢確認」精簡 UI。
- **做到此批時，必須重新向使用者確認責任聲明正式文字、Checkbox 與否，以及已收回／未收回證明聯等覆核流程。**

### 第五批：同步與 UI 收尾

- `cancel_date` / 作廢狀態同步。
- 已開立清單與詳細資訊一致呈現。
- PDF / preview Cache 必要失效處理。
- issue center 必要整合。
- 回歸測試與 Windows 工程測試包。
