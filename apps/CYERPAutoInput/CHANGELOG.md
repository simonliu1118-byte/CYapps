# CYERPAutoInput 版本紀錄

本檔保存可確認的歷史事實。正式 Release 為 V0.2.9（2026-10-12，tag `cyerp-auto-input-v0.2.9`）；先前發布的 V0.2.7（tag `cyerp-auto-input-v0.2.7`）已依使用者要求刪除，由 V0.2.9 取代。V0.2.6 以前皆為工程測試版。C# 重寫線（V0.1.0 起）於 2026-10-11 以 PR #104 squash merge 進 `main`（V0.2.0 Build 31），取代舊 Go 線 `V0.0.10 Build 19`；V0.2.1–V0.2.3 Build 1 以 PR #398、V0.2.4 以 PR #418、V0.2.5–V0.2.7 以 PR #421、V0.2.7 Build 1–V0.2.9 以 PR #423 合併。實機結果以 `WORK_HANDOFF.md` §4 為準。

## V0.3.0 — 2026/10/12（開發中）

- Build 4（2026/10/13）：蝦皮全自動支援 7-ELEVEN（使用者 2026-10-13 提供畫面）。清單與明細的物流方式為 7-ELEVEN 時，一樣按「安排出貨」，「查看寄件編號」顯示的是交貨便代碼（例如 G＋11 碼數字），按「列印寄件單」後會開 7-11 的交貨便服務單分頁（沒有列印按鈕）：核對單上的「寄貨訂單編號」與「交貨便服務代碼」後按 Ctrl+P 叫出 Chrome 列印，目的地須為設定的印表機、縮放 100%（設定新增「7-11 縮放 %」，預設 100）才列印。Chrome 列印視窗的「縮放比例」在「顯示更多設定」收合時看不到，現在讀不到縮放比例時會先點開「顯示更多設定」一次（蝦皮店到店也適用）。印完關閉分頁、按 × 回到訂單頁、光學辨識與 ERP 流程與蝦皮店到店相同。全家、萊爾富之後再加。

- Build 3（2026/10/13）：Build 2 實測仍停在第一個清單畫面。LOG 的堆疊顯示是文字辨識元件在計算「每個字的位置」時出錯（不是網頁沒載完：程式會反覆讀畫面直到清單出現，最多等 30 秒）；而且逐字切開的結果會把「訂單編號 2610…」拆成兩塊，清單本來就認不出來。蝦皮全自動改用另一個只回傳整行文字的辨識器（同一套模型），不再計算逐字位置。依使用者截圖實際辨識的結果補強：「建議今天内出貨」（內讀成内）、「待虚理」（處讀成虚）、「包里」（裹讀成里）都認得；清單第一筆有「在1天內確認」標籤時，物流方式在「待出貨」上方也讀得到；寄件編號最後一碼 O／0 兩個畫面讀得不同時視為同一號碼；「查看寄件編號」的 × 有讀到就點它，沒讀到才用像素找。每次讀畫面在 LOG 記一行判斷結果（清單／明細／寄件編號視窗／預覽列印／列印視窗）。

- Build 2（2026/10/13）：實測蝦皮全自動一開始就停止「Index was outside the bounds of the array」：開好 Chrome 讀清單頁時，文字辨識引擎對整個視窗的辨識內部出錯（LOG 只有例外名稱）。整窗辨識失敗時改為把同一張畫面切成上下兩半（重疊 80 px）各辨識一次再合併；LOG 的錯誤加上呼叫堆疊，下次能看出出錯的位置。

- Build 1（2026/10/13）：ERP 商品明細的欄位排法每台電腦可能不同（使用者 2026-10-13：另一台「批號」在「庫別名稱」之後）。開始輸入明細時，建立第一列的那一下改為先辨識表頭的「品號」，點它下面的第一列；原本是點明細區寬度 5.2% 的固定位置，欄位排法不同就點不到（讀不到表頭時才用舊位置）。各欄的左右順序也從表頭讀出來，水平捲動找欄位時照實際順序，不再假設固定順序；「庫別」不會誤認成「庫別名稱」。明細列高固定 22 px（使用者確認不會變），量不到時以 22 px 計算。

- Build 0（2026/10/12）：新功能「蝦皮全自動」（「蝦皮」按鈕選單）：程式開一個自己的 Chrome 新視窗（一般 Chrome、已登入的蝦皮賣家中心，不碰其他分頁），進到「我的銷售 › 待出貨 › 待處理」，逐筆處理到沒有待處理訂單：
  1. 先看「建議今天內出貨」，沒有訂單就點「建議出貨期限」那一列的「全部」（不是訂單狀態的「全部」）。
  2. 點第一筆訂單的「待出貨」開啟訂單明細（新分頁）；核對訂單編號，物流方式只做蝦皮店到店（含隔日到貨）與蝦皮店到宅。
  3. 按「安排出貨」或「安排取件」：只在文字完整讀到、在「待出貨」卡片內、是橘色、且完全在「不成立訂單」右側不重疊時才按，否則停止。
  4. 等「寄件編號申請中」變成 TW 寄件編號 → 按「列印寄件單」（看不到就在視窗內往下捲）→ 等預覽列印頁「已下載完成、1 個包裹、0 個失敗」→ 核對寄件單上的訂單編號與寄件編號 → 按「列印出貨文件」。
  5. Chrome 列印視窗：目的地與縮放比例必須等於設定（「設定 › 平台匯入 › 蝦皮」新增寄件單印表機，預設 GG-D410 Printer；寄件單縮放，預設 110%）才按「列印」，不自動改。
  6. 關掉預覽列印分頁，按「查看寄件編號」右上角的 × 回到訂單頁 → 光學辨識（核對訂單編號、物流單號＝寄件編號）→ 輸入 ERP、儲存並列印。
  7. 關掉訂單分頁，回到清單分頁按 F5，處理下一筆。全部完成後關閉這個 Chrome 視窗。
  - 任何一步讀不到、對不上、逾時，或訂單有需人工確認的項目（光學辨識提醒、ERP 轉人工／庫存不足／未儲存／未列印），整批停止並發出聲音，告訴使用者停在哪一筆、蝦皮是否已安排出貨。按 Esc 隨時停止。同一筆不會處理兩次。
  - 原本設定的「蝦皮全自動」改名為「蝦皮自動擷取」（功能不變）。

## V0.2.9 — 2026/10/12（正式 Release：tag `cyerp-auto-input-v0.2.9`，取代 V0.2.7）

正式版，彙整 V0.2.7 之後的修改（使用者 2026-10-12 實測通過）：

- 套裝商品「A+B」（蝦皮、MO店+、酷澎都適用）：拆成各品號輸入，單價由 ERP 帶出原價，原價與套裝售價的差額併入促銷組合；套裝售價高於原價合計時轉人工。
- 瀏覽器按 F8 即開啟蝦皮光學辨識並開始擷取（設定可關閉）。
- 一般輸入也顯示「自動輸入中」；結束時顯示綠色完成、黃色需確認／中斷、紅色「使用者已停止」；按 Esc 立即停止。
- 帶入表單時商品依品號由小到大排列（折價券、運費、促銷組合在最後）。
- 蝦皮光學辨識：編號、單號 1／I、7-ELEVEN 貨運別等誤讀修正；數量讀錯時提醒會指出最可能的那一項（不自動修改）；說明改為目前流程。

- Build 0（2026/10/12）：新功能（含 V0.2.8 Build 4 尚未發出的修改）。蝦皮套裝商品：商品選項貨號為「A+B」（OCR 讀成 ＋ 或「十」也算）時拆成各品號，數量都等於套數（某段寫成「Bx2」則該品號再乘 2）。為了讓報表上每個品號的金額正確（使用者 2026-10-12），套裝品項只輸入品號與數量、不填單價，由 ERP 帶出原價，程式再從 ERP 讀回這個單價；各品項原價×數量的合計與套裝售價的差額，併入促銷組合（例：250＋160＝410，套裝 400 → 差 10／套，連同原本的促銷折扣一起打在 Z902）。有套裝時一定會有促銷組合那一列；讀不到 ERP 單價、或促銷組合不在套裝之後時停止並提醒人工處理，不會猜。排序時同一套裝的品項放在一起。套裝售價高於 ERP 原價合計時停止、轉人工處理。所有來源（蝦皮光學辨識、蝦皮匯出檔、MO店+、酷澎）的套裝都照這個方式處理（使用者 2026-10-12）；MO店+／酷澎原本「組合品號轉人工」改為拆品號輸入，只有沒設定促銷組合品號時才轉人工。

## V0.2.6 — 2026/10/12（工程測試中，與 V0.2.7 一起發布；實測 12 項訂單通過）

- Build 0（2026/10/12）：第 7 項商品起輸入失敗「ERP 明細 row=7, column=0 連續兩次都沒有進入編輯模式」（使用者實測 12 項的訂單）。原因：明細第 2 列以後的位置以固定列高 24 px 推算，但這台 ERP 的列高是 22 px，誤差逐列累積，第 7 列時點到該列下方空白處。改為每張單據從 ERP 實際開啟的編輯框位置量測列高（第 1 列與前 6 列中最遠的一列），第 1 列也以實際編輯框為準；量不到或數值異常時才用 24 px。編輯框未就緒時 LOG 另記編輯框位置與明細頂端，便於排查。

## V0.2.5 — 2026/10/12（工程測試中，與 V0.2.6 一起發布）

- Build 0（2026/10/12）：訂單編號／運送單號的 0 與 O（使用者回報末段英數混合處偶爾讀錯）。
  - 訂單編號前 6 碼是日期，讀到的 O 一律改為 0。
  - 運送單號：蝦皮店到店 `TW` 後面 12 碼是數字，其中的 O 改為 0（最後一碼照讀到的）；新竹、黑貓等全數字單號的 O 改為 0。
  - 訂單編號後 8 碼英數混合，0 與 O 都可能出現：改以截圖中的字寬判斷。蝦皮字型的 0 與其他數字同寬，O 約寬三分之一；先依常見字寬把相連的字對齊，只有單獨成一塊、且同一串有至少兩個數字可比較時才判斷，比值 ≤1.12 為 0、≥1.25 為 O，其餘照 OCR。判斷過程寫入 LOG。
  - 商品選項貨號不自動轉換（無法確定品號沒有字母 O）。
